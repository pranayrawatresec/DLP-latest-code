On-Premise Endpoint DLP  ·  Internal Engineering Report

Blocking Sensitive
File Uploads in the Browser

An engineering audit of the DLP Upload Guard extension and its native host: what we built, the bugs and logic holes in it today, how far it is from the goal of “no sensitive file leaves this PC through a browser”, and the architecture that would actually get us there.
Scope: dlp-browser-ext/ · dlp-agent/src/browser_host.rs · cmd_browser_host in main.rs
Audience: engineers, product, and anyone who needs to understand the risk — no browser expertise assumed
Date: 9 September 2026  ·  Feature status: built and unit-tested; never yet run in a real browser
Bottom line up front. The feature is a well-shaped skeleton, but as it stands it would not stop a determined user, and it misses several everyday, entirely innocent upload paths — including uploads to Amazon S3, Google Drive and OneDrive, which is precisely the goal we set. Five defects are severe enough that the block can be bypassed with no technical skill at all. None of them are hard to fix.

1. Executive summary

In one paragraph, for a non-engineer: We built a small program that lives inside Chrome and Edge. When you attach a file to a web page, it copies the first few megabytes of that file, asks our DLP agent “is this classified?”, and cancels the upload if the answer is yes. The idea is right. The problem is that this program lives inside the web page, where the page can see it and talk back to it — and several of the places it tries to say “stop” are places where the browser has already stopped listening.

The five things that matter most

  1. Paste and drag-and-drop are never actually blocked. The code tries to cancel the action after it has already happened. The user sees a red “blocked” banner while the classified text sits in the Gmail message body. That is worse than no protection, because it looks like protection and files an incident claiming success.
  2. Any web page can approve its own uploads. The verdict travels through a channel the page can also write to. Three lines of JavaScript — in the page, or pasted into the console by a curious user — turn every verdict into “allow”.
  3. Anything we cannot read, we let through. Password-protected ZIP, encrypted DOCX, an unusual format, a fragment of a file — all produce “no match found”, which we treat as “safe”. Our USB channel already has a setting for exactly this case. The browser channel does not.
  4. Uploads to S3, Google Drive, OneDrive and Dropbox are not covered. Those services never send a file in one piece; they slice it into chunks. Each chunk on its own is meaningless bytes, so every chunk is judged clean and the whole classified document lands in the cloud.
  5. We only look at the first 4 MB. Put the secret on page 200 of a large PDF, or simply pad the file, and we never see it — and we never record that we did not see it.
Honest framing for the customer. Today this feature is a deterrent and an audit trail for the accidental leak — the employee who attaches the wrong document to an email. It is not yet a control against someone who is trying. It should not be described as “blocks uploads” in a proposal or demo script until Phases 1 and 2 of the roadmap in §8 are complete.

What is genuinely good about what we have

  • The architecture split is correct. The browser part is deliberately dumb; the agent holds the detection engine, the fingerprints and the thresholds. No detection data ships inside the browser, where it could be extracted and studied.
  • The native-messaging protocol is clean, versioned and unit-tested — framing, verdict mapping and incident construction all have real tests in browser_host.rs.
  • No content is ever logged or transmitted. Incidents carry hashes, scores, a matched document title and the destination URL only. This holds up under review and matches the product’s non-negotiable rules.
  • Binary files really are content-inspected, not judged by filename — the extension reads the bytes and the host runs the same extraction engine as the USB and clipboard channels.
  • The existing documentation is unusually honest about its own limits. That is rare, and worth preserving as the feature grows.

2. What this feature is supposed to do

Stated plainly: a classified document on an employee’s PC must not be able to leave through a web browser — not as a Gmail or Outlook Web attachment, not into SharePoint or Google Drive, not into an S3 bucket, not onto a file-sharing site, not pasted into a chat box, and not dragged onto a random web page.

This is one of the escape routes the product tracks (alongside USB, clipboard, print, desktop email and the network itself). It is the hardest one, for one specific reason:

Why the network filter alone cannot do this. Our network filter (WFP) can see that Chrome is connecting to drive.google.com on port 443. It cannot see what is inside that connection, because the connection is encrypted end-to-end by TLS. It can only make destination-based decisions: allow this site, block that one. To decide based on the content of an upload, something must look at the data before the browser encrypts it. That is the entire reason the browser extension exists.

3. What we built

Four moving parts, in the order data flows through them.

The journey of one file, step by step

  1. An employee opens Gmail, clicks Attach, and picks OPORD.pdf.
  2. Chrome fires a change event. Our content.js sees it first.
  3. content.js decides the file is binary (not a .txt), reads the first 4 MB, and base64-encodes it — turning raw bytes into a long text string so they can travel through Chrome’s messaging system.
  4. It hands that to background.js, which forwards it down a pipe to dlp-agent.exe browser-host.
  5. The agent decodes it and runs the document-fingerprint engine, producing a score: e.g. “42% of this content matches the registered document Operation Himalayan Shield”.
  6. Containment ≥ 0.30, or coverage ≥ 0.60, or any exact-data (EDM) match ⇒ block. A weaker match ⇒ warn. Nothing ⇒ allow.
  7. The verdict travels back. On block, content.js clears the file input, shows a red banner, and remembers the input so that a later form submit is cancelled too.
  8. The agent raises an incident to the management server over mutual TLS — file hash, score, matched title, destination URL. If the server is unreachable it queues locally and flushes later.
Two terms you will keep seeing. Isolated world = a private JavaScript sandbox Chrome gives extensions; the web page cannot see or touch anything in it. MAIN world = the page’s own JavaScript space; anything we place there, the page can read, rewrite or delete. We are forced into the MAIN world in order to intercept fetch(), and almost every serious problem in this report traces back to that single fact.

4. Findings

Twenty-two issues, ordered by severity. Each names the file, explains the mechanism in plain terms, states the real-world consequence, and gives the fix.

P0 — Critical: the block does not hold

P0-1Paste and drag-and-drop are never actually blocked

dlp-browser-ext/content.js — the 'drop' handler (~line 196) and the 'paste' handler (~line 222)
What is wrong
Both handlers are declared async and call ev.preventDefault() only after await scanFile(...) returns.
Why it happens
A browser event can only be cancelled while it is still being delivered. The moment our handler reaches its first await, it returns control to the browser; the browser finishes delivering the event and performs the default action — pasting the text, or handing the dropped file to the page. Our preventDefault() arrives milliseconds later and is silently ignored. There is no error and no warning: the code reads as if it works.
What it means
Copy a classified paragraph and paste it into a Gmail compose window — the text lands in the message. Drag a classified PDF onto a file-sharing site — the site receives it. In both cases our red banner appears on top of the successful leak, and an incident is filed recording action_taken = Blocked. A wrong audit trail is worse than a missing one, because it will be believed.
Fix
Use the standard block-then-replay pattern: cancel unconditionally and synchronously, hold the payload, scan it, and re-insert it into the page only on an allow verdict. For paste that means preventDefault() immediately, then writing the text back with insertText on allow. For drop it means swallowing the drop and re-dispatching a synthetic DataTransfer on allow. Both patterns are well established; both need real browser tests, which we have never run.

P0-2A web page can approve its own uploads

dlp-browser-ext/inject.js:31–56 (the 'res' listener) and content.js (~line 296)
What is wrong
The verdict travels from content.js to inject.js as window.postMessage({__dlp:'res', id, verdict}). That is a public broadcast inside the page. Every script on the page can listen to it and, crucially, can send one. The request ids are simply 1, 2, 3…
Why it happens
inject.js must live in the page’s own JavaScript world in order to wrap fetch(). Extensions have no private channel into that world, so the code uses the only bridge available. This is not a coding slip — it is a consequence of putting the decision inside the page at all.
What it means
This defeats the whole fetch/XHR path, which is the path that covers Gmail, Drive, SharePoint and essentially every modern site. The bypass fits on one line, needs no privileges, no admin rights and no installed software: 
// pasted into the browser console, or shipped in any page's own script
setInterval(()=>{for(let i=1;i<9999;i++)postMessage({__dlp:'res',id:i,verdict:'allow'})},5)
The message names are visible in the page, so a merely curious user can find this.
Fix
Stop treating the page-world hook as the enforcement point (§6 and §7). Short term, make forgery impractical: unguessable random ids, and accept replies only over a MessageChannel port handed across once at document_start before any page script runs. Long term, enforce in the service worker with declarativeNetRequest or blocking webRequest, where the page gets no vote at all.

P0-3Content we cannot read is treated as safe

dlp-agent/src/browser_host.rs — map_verdict (~line 175)
What is wrong
map_verdict looks only at the match lists. It never inspects verdict.extraction. When the engine returns Extraction::Unreadable — encrypted ZIP, password-protected Office file, unsupported format, corrupt header — the match lists are empty, so the mapping produces allow.
Why it happens
An oversight, not a decision: the same team wrote the correct handling elsewhere. kguard/mod.rs:1213 explicitly checks for Unreadable and applies a configurable [kguard] fail_block on the exfiltration path. The browser channel never received that check.
What it means
“Right-click → add to archive → set a password” defeats content inspection entirely — and employees do that for legitimate reasons every day, so it will not look suspicious in a review. This also directly contradicts product rule B4 — fail secure on unreadable egress from the Tier 2 plan.
Fix
Add the Unreadable branch to map_verdict, honouring a [webupload] fail_block knob mirroring [kguard] fail_block. Sensible production default: unreadable content bound for a non-sanctioned destination is blocked; bound for a sanctioned one it is warned and audited.

P0-4Cloud uploads (S3, Drive, OneDrive, Dropbox) are not covered

dlp-browser-ext/inject.js — partsFromBody (~line 98); architectural
What is wrong
We scan whatever is handed to a single fetch() call. Every serious cloud storage service instead performs a resumable or multipart upload: the page slices the file with file.slice(start, end) and sends the pieces as separate requests, typically 256 KB to 8 MB each.
Why it happens
We inspect each slice in isolation. A slice is a headerless fragment of a PDF or DOCX; our extractor cannot identify the format, extraction fails, no match is found, and the verdict is allow. This compounds P0-3: every chunk of every large upload becomes an “unreadable, therefore safe” decision.
What it means
The single most-cited goal for this feature — stop uploads to cloud storage and S3 — is not met, and it fails silently and consistently rather than occasionally. A demo using a small file on a simple HTML form will pass cleanly and hide this completely.
Fix
Two complementary moves. (a) Session reassembly: recognise the resumable protocols (Google’s uploadType=resumable, S3 CreateMultipartUpload, Microsoft’s createUploadSession) and correlate chunks back to one logical upload. (b) Better — decide on the source file, not on the bytes on the wire, by correlating with the kernel driver, which already observes Chrome opening the real file on disk (§7, Layer 1). Option (b) also resolves P0-5 and most of the performance problems in one move.

P0-5Only the first 4 MB of a file is ever examined

content.js:24 MAX_SCAN_BYTES · inject.js:25 · browser_host.rs MAX_SCAN_BYTES
What is wrong
The cap is applied by truncation, and truncation is then treated as a complete scan. A 60 MB PDF is judged on its first 4 MB; the remaining 56 MB is never seen and never recorded as unexamined.
Why it happens
The cap itself is a sensible memory and latency limit, copied from the kernel path. The mistake is the missing disposition for the part we skipped.
What it means
Deliberate evasion is trivial — prepend 4 MB of holiday photos. Accidental misses are just as likely: a scanned 200-page classified annex easily exceeds 4 MB, and the sensitive pages are rarely at the front.
Fix
Stream the whole file through the fingerprint engine rather than buffering a prefix — the engine already works on rolling windows, so this is a plumbing change, not a maths change. Where a hard cap must remain, mark the verdict Partial and apply the same fail-secure rule as P0-3 instead of implying the scan was complete.

P1 — High: large holes in coverage

P1-1Most request body types are not inspected at all

dlp-browser-ext/inject.js — partsFromBody (~line 98)
What is wrong
We only recognise three body shapes: File, Blob and FormData. Everything else passes untouched.
What it means
Not covered: a plain string body (very common — a single-page app reads the file itself with FileReader and posts JSON containing base64), an ArrayBuffer or typed array, URLSearchParams, a ReadableStream, and a body passed inside a Request object (inject.js:139 explicitly gives up on that case). Also unhooked entirely: navigator.sendBeacon, WebSocket, and WebRTC data channels.
Fix
Handle string/ArrayBuffer/typed-array bodies, and tee ReadableStream bodies. Accept that a list of body shapes will never be complete — which is the argument for the default-deny model in §7 rather than an ever-growing allowlist of shapes we understand.

P1-2An about:blank iframe has no hook in it

dlp-browser-ext/manifest.json — content_scripts
What is wrong
The content scripts declare all_frames: true but omit match_about_blank (and match_origin_as_fallback). Chrome does not inject into frames with no real URL unless those are set.
What it means
A three-line bypass: create an empty <iframe>, take its untouched fetch, upload with it. Same origin, same cookies, no hook. Pages using srcdoc, blob: or sandboxed frames are likewise uncovered.
Fix
Add "match_about_blank": true and "match_origin_as_fallback": true. One-line change; then verify in a browser.

P1-3The name-only fallback is effectively “allow”

content.js — scanFile fallback; browser_host.rs — ScanKind::ScanFile
What is wrong
When the extension cannot read a file’s bytes it falls back to scan_file, sending only the filename. The host then calls detect::verdict(Path::new("OPORD.pdf")), which tries to open that name as a path on disk, relative to the host process’s working directory. It does not exist, the read errors, and handle_request converts errors into allow with a reason.
What it means
Every path that fails to read bytes silently succeeds in uploading. The fallback that exists to be conservative is the least conservative branch in the file.
Fix
Delete the scan_file path from the browser channel, or make it fail-secure. If we cannot read the content, we cannot clear the upload.

P1-4Internal errors fail open, contradicting the stated posture

inject.js — the fetch wrapper's catch block (~line 148)
What is wrong
The whole hook body is wrapped in try { ... } catch (_e) { /* fall through */ } and then calls the real fetch. Any unexpected error — and hooking arbitrary sites produces plenty — results in the upload proceeding unscanned.
What it means
The extension advertises fail-secure (SCANNER_UNAVAILABLE_VERDICT = 'block') but the most likely failure mode in practice, an exception in the hook, fails open. A page can also deliberately provoke one.
Fix
Route hook exceptions into the same fail-secure decision as a scanner timeout, and raise an incident so the operator can see the extension is malfunctioning on a given site.

P1-5Pasted files and images are not scanned

dlp-browser-ext/content.js — the 'paste' handler
What is wrong
The handler reads clipboardData.getData('text/plain') only. It ignores clipboardData.files and image items.
What it means
Copy a classified file in Explorer, click into Gmail’s compose window, press Ctrl+V — the file is attached and never scanned. Screenshot a classified document and paste the image — likewise (image content also needs OCR, which is separate work already under way in the repository).
Fix
Scan clipboardData.files through the same path as a file input, and route image items to the OCR pipeline once it lands.

P1-6A fail-secure block leaves no audit trail

background.js — unavailableReply; content.js — requestVerdict
What is wrong
When the native host is missing, crashed or slow, the extension blocks the upload by itself. Incidents, however, are raised by the host — which by definition is not there.
What it means
Enforcement happens with no record: the console shows nothing, the user sees an unexplained block, and support cannot distinguish “DLP correctly blocked a leak” from “the agent is broken on this machine”. This breaks the product rule that every enforcement action is audited.
Fix
Buffer enforcement events in the service worker (chrome.storage.local) and flush them to the agent when it returns; have the agent post a ScannerUnavailable incident. Surface a per-endpoint browser-channel health state in the console (see §7, Layer 4).

P2 — Medium: correctness, operability and privacy

P2-1Every file is scanned at least twice

content.js 'change' handler + inject.js fetch/XHR hook
What is wrong
Picking a file triggers a full 4 MB read, base64 encode and native round-trip. The page then uploads the same file, and the fetch hook does all of it again. There is no cache keyed on content hash.
What it means
Doubled latency and memory on every upload (a 4 MB file becomes a ~5.5 MB string, copied several times), and two incidents on the server for one user action — which will inflate incident counts and confuse reviewers.
Fix
Hash first (streaming SHA-256), then consult a short-lived verdict cache in the service worker keyed on hash + destination origin. Scan once, decide many times.

P2-2The first upload after a restart is likely to be blocked

background.js SCAN_TIMEOUT_MS = 8000; main.rs cmd_browser_host (bundle load)
What is wrong
The first scan after the service worker starts must spawn dlp-agent.exe, which loads and verifies the fingerprint bundle before it can answer. If that exceeds 8 seconds, the extension applies its fail-secure block.
What it means
On a cold or loaded machine, users get an unexplained block on their first upload, which succeeds when they retry. Users learn very quickly that retrying defeats DLP — a behaviour we do not want to teach.
Fix
Have the host answer a cheap ping immediately and load the bundle in the background; keep the host warm as part of the DLP service rather than spawning it per browser profile; distinguish “starting up” from “unavailable” and hold the upload rather than failing it.

P2-3The XHR wrapper changes browser semantics

inject.js — XMLHttpRequest.prototype.send wrapper
What is wrong
send() now returns immediately while the real send happens later, after an async scan. Code that calls abort(), sets timeout, or listens to upload.onprogress between those two moments behaves differently from a normal browser.
What it means
Site breakage that will be blamed on DLP, and support cost. In particular an abort() during the scan window is ignored, and we then send the request anyway.
Fix
Track per-request state, honour an abort() that arrives during the scan, and add regression tests against a harness page that exercises each XHR lifecycle event.

P2-4The block banner tells the page what it matched

content.js — verdictText / showBanner
What is wrong
The banner text includes the matched document’s title and is inserted into the page’s own DOM, where any script on that page can read it.
What it means
A hostile or compromised site learns the titles of classified documents on the endpoint, and an insider gets a clean oracle for probing what is registered. This directly contradicts notify/mod.rs, which deliberately hides detection internals as “evasion intel for an insider”.
Fix
Show a neutral message plus a case reference (“Blocked by DLP — reference A7F32C”) and put the detail only in the incident and the desktop toast. Render the banner in a closed shadow root so the page cannot read or restyle it.

P2-5No stable extension identity, so it cannot be deployed as designed

manifest.json — no "key", no icons; install-native-host.ps1 -ExtensionId
What is wrong
Without a key in the manifest (or a packed CRX), the extension’s 32-character id is derived from its install path and differs per machine. But the native host pins that id in allowed_origins, and enterprise force-install policy addresses it by id too.
What it means
The documented deployment path cannot actually work at scale as written. There are also no icons, so the extension is unidentifiable in the browser UI.
Fix
Generate a signing key once, pin "key" in the manifest, produce a signed CRX, and host an update XML on-premise for air-gapped sites. Add icons and a minimal options page showing health and version.

P2-6The install script probably writes a manifest Chrome will reject

install-native-host.ps1 — Set-Content ... -Encoding utf8
What is wrong
On Windows PowerShell 5.1 — the version present on a stock Windows endpoint — -Encoding utf8 writes a UTF-8 byte-order mark at the start of the file. Chrome parses the native-host manifest with a strict JSON reader.
What it means
A likely “native host not found” failure at install time that is painful to diagnose, because everything looks correct on screen. Verify this on a real endpoint before shipping — it has never been run end to end.
Fix
Write the manifest with [System.IO.File]::WriteAllText using a UTF8Encoding($false), or plain ASCII. Separately, add %* to the .cmd launcher so Chrome’s calling-origin argument reaches the host, and have the host verify it — defence in depth alongside allowed_origins.

P2-7Policy is local to each endpoint, not delivered by the server

main.rs cmd_browser_host — block_at / coverage_block_at from [kguard]
What is wrong
Thresholds come from the agent’s local config file. There is no per-group policy for this channel, no sanctioned/blocked origin list, no per-destination action, and no user-justification or break-glass workflow.
What it means
Every other channel in the product is administered from the console; this one is not. An administrator cannot say “uploads to our own SharePoint are fine, everything else is blocked” — which is the single most useful rule this feature could offer.
Fix
Define a web-upload policy object served over mTLS alongside the other policies: sanctioned origins, per-origin action, thresholds, fail-secure switches, and an override workflow with audited justification.

P2-8[webupload] trusted_origins is parsed but wired to nothing

dlp-agent/src/config.rs:559–585 — no consumers outside config.rs
What is wrong
The configuration section exists, parses, and has unit tests. No code reads it. It was intended to seal rather than block uploads to sanctioned destinations.
What it means
An administrator can write configuration that appears to be accepted and silently does nothing — the most dangerous kind of setting in a security product.
Fix
Either implement it as part of P2-7, or remove it and fail loudly on an unknown section until it is implemented.

P2-9No tests, no linting, no build, never run in a browser

dlp-browser-ext/ — 7 files, no package.json, no CI
What is wrong
The Rust host has good unit tests. The ~700 lines of JavaScript that make every actual enforcement decision have none, and the extension has never been loaded into Chrome. Every P0 in this report would have been caught by a single manual test.
Fix
A test harness page with one button per upload vector, driven by Playwright against a real Chrome with the extension loaded and a stub native host; unit tests for the decision logic; both in CI. See §9.

P3 — Strategic

P3-1Coverage stops at Chrome and Edge, and is switchable off

What is wrong
Firefox is unsupported. A portable browser downloaded to the Desktop is unsupported. Starting Chrome with --disable-extensions turns the feature off, including a policy-installed extension.
What it means
For a defence customer, “the control is off unless the user cooperates” is not a control. This is not fixable inside the extension.
Fix
Enforcement attestation plus a network kill-switch: the agent watches for browser processes, expects a heartbeat from the extension, and uses the existing WFP filter to block egress for any browser process that is not attested. Details in §7, Layer 2.

P3-2The two halves fail in opposite directions

What is wrong
The extension fails secure (host missing ⇒ block). The host fails open (no fingerprint bundle cached ⇒ allow everything, audit only, main.rs:1456).
What it means
The combined behaviour is neither. On a freshly enrolled machine that has the host installed but has not yet received a bundle, every upload is allowed — and this is the exact state of a machine during its first hours in the field. Both behaviours are documented, but together they are not a coherent posture.
Fix
One switch, one owner, one documented default: no usable policy means uploads to non-sanctioned destinations are blocked and the endpoint is reported as degraded in the console.

6. Why a hook inside the page can never be the whole answer

This is the single most important idea in the report, and it is worth stating carefully, because it determines what we build next.

To intercept fetch(), our code has to run in the page’s own JavaScript world. In that world, our code and the page’s code are peers. They can read each other, overwrite each other, and race each other. There is no privilege boundary. Anything we do there is by consent, not by force.

An analogy. Imagine posting a security guard inside a room, and giving the people in that room the power to rewrite the guard’s instructions, imitate his radio, or simply ask him to step outside. He will stop honest people who make a mistake. He will not stop anyone who does not want to be stopped. To actually control the door, the guard has to stand outside the room.

The practical consequences:

  • The page-world hook is a good content extractor — it is the only place with easy access to the file object. It is a poor enforcement point.
  • Enforcement must live where the page has no reach: the extension’s service worker (which can cancel network requests), the agent, the network filter, and the kernel driver.
  • Coverage should not be an ever-growing list of transports we remember to hook. It should be default-deny: an upload that we have not positively cleared does not go out.

7. What production grade looks like

Four layers. Each one catches what the layer above it misses, and each is independently useful. Three of the four reuse components this project already has.

Layer 1 — Use the kernel to solve the hard content problems

This is the highest-leverage idea in the report. Our minifilter already watches chrome.exe open files and already classifies content from the file system stack. When the extension reports “an upload of OPORD.pdf, 12 MB, is starting”, the agent can correlate that with the file the browser just opened on disk and make its decision against the complete, real file.

That one change removes four separate problems at once: the 4 MB truncation (P0-5), chunked cloud uploads (P0-4), the base64 copying overhead (P2-1), and the fragment-is-unreadable failure (P0-3 as it applies to chunks). It also gives read-deny as a hard backstop: for the highest classifications the browser can simply be denied the read, and no amount of JavaScript trickery creates data the browser was never given.

Layer 2 — Make the browser prove it is protected

The answer to Firefox, portable browsers and --disable-extensions is not more extension code. The agent should watch for browser processes and expect a periodic heartbeat from our extension inside each one. A browser process running without a valid heartbeat is unattested, and the existing WFP filter blocks its network egress by application id. The user gets a clear message: this browser is not protected, use the managed one.

Combined with a destination allowlist — only sanctioned SaaS reachable at all — the content-inspection job shrinks from “the whole internet” to “the handful of sites we approved”, which is a problem we can actually solve well.

Layer 3 — A hardened extension, built default-deny

Invert the model. Instead of “let everything through unless we spot something bad”, the service worker cancels any request carrying a body to a non-sanctioned destination unless it holds a fresh approval for that exact content hash, tab and origin. The page-world hook is demoted to a content extractor whose output is treated as untrusted input; it can no longer grant permission, only supply material for a decision made elsewhere.

Concretely:

  • Enforce with declarativeNetRequest or blocking webRequest in the service worker. Verify against your Chrome channel: blocking webRequest remains available to policy force-installed extensions, which is exactly our deployment model — confirm before designing around it.
  • Block-then-replay for paste and drop, so cancellation is synchronous and correct.
  • Hash first, cache verdicts by content hash, scan once.
  • Recognise resumable-upload protocols and decide per logical upload, not per chunk.
  • Unreadable, oversized or unrecognised content follows a configured fail-secure rule, not an accidental allow.
  • Neutral in-page messaging in a closed shadow root; details go to the incident and the desktop toast only.
  • Signed CRX with a pinned key, icons, an on-premise update feed, and GPO/Intune templates for Chrome and Edge.

Layer 4 — Assurance, because a silent control is not a control

  • A console page listing every endpoint’s browser-channel state: extension version, host reachable, bundle age, last heartbeat, enforcing or degraded.
  • An incident for every enforcement action, including fail-secure blocks and scanner outages, so “blocked correctly” and “broken” are distinguishable.
  • A user-facing block dialog with a case reference and, where policy allows, a justification workflow that records who overrode what and why.

8. Roadmap

Sequenced so that each phase leaves the product in an honest, shippable state. Estimates assume one engineer familiar with the codebase, and include the browser testing that has never been done.

~1–2 weeks

Phase 1 — Make the existing feature true

No new capability; make what we claim actually happen.

  • Fix P0-1 (block-then-replay for paste and drop) and P0-3 (unreadable ⇒ fail-secure).
  • Harden the verdict channel against forgery (P0-2, interim mitigation).
  • Fix P1-2 (match_about_blank), P1-3 (name-only fallback), P1-4 (fail-open catch), P1-5 (pasted files), P1-6 (incidents for fail-secure blocks).
  • Fix P2-6 (install script encoding) and P2-5 (pinned key, icons, signed CRX).
  • Stand up the test harness and CI (P2-9), and run the extension in a real browser for the first time.

Exit criteria: every P0 and P1 closed, verified by an automated browser test, and Test E2 in the deploy guide actually ticked.

~2–4 weeks

Phase 2 — Default-deny and real policy

  • Move enforcement into the service worker; page hook becomes an extractor only (closes P0-2 properly).
  • Chunked and resumable upload handling (P0-4), plus body types beyond File/Blob/FormData (P1-1).
  • Server-delivered web-upload policy: sanctioned origins, per-origin action, thresholds, fail-secure switches (P2-7, P2-8, P3-2).
  • Verdict cache and hash-first scanning (P2-1); warm host, no first-upload block (P2-2).
  • User-facing block dialog with case reference and justification workflow (P2-4).

Exit criteria: a classified file cannot be uploaded to S3, Drive, OneDrive, Dropbox, Gmail or a pastebin from a managed Chrome, demonstrated live.

~3–6 weeks

Phase 3 — Close the ways around the browser

  • Kernel path correlation: decide on the whole real file, not on wire bytes (P0-5, P0-4).
  • Attestation watchdog plus WFP kill-switch for unattested browser processes (P3-1).
  • Console assurance view and channel-health telemetry (Layer 4).
  • Firefox support (WebExtensions; native messaging works the same way).

Exit criteria: an unmanaged or extension-disabled browser cannot reach the internet at all; the console can prove, per endpoint, that the channel is enforcing.

follow-on

Phase 4 — Depth

  • OCR for images and screenshots (work already started in the repository).
  • Desktop email (Outlook MAPI/VSTO) and desktop chat clients.
  • Third-party penetration test aimed specifically at this channel, with the bypasses in §4 as the starting checklist.

9. How we will know it works

The root cause of every P0 in this report is the same: the JavaScript was never executed in a browser. The fix is not more review — it is a harness.

  • A vector harness page served locally, with one button per upload path: simple form, form with a large file, drag-drop, paste text, paste file, paste image, fetch with File, with Blob, with FormData, with a string body, with an ArrayBuffer, with a Request object, XHR variants, sendBeacon, chunked upload, upload from an about:blank iframe, upload from a Web Worker.
  • Driven by Playwright against a real Chrome with the extension loaded and a stub native host that returns a scripted verdict, asserting on what the server actually received — not on whether a banner appeared. Data arriving at the destination is the only definition of failure that matters.
  • Adversarial tests as first-class citizens: the forged-verdict bypass, the about:blank bypass, the password-protected ZIP, the 4 MB-padded file, and the chunked upload each become a permanent regression test.
  • Fault-injection tests: host missing, host slow, host killed mid-scan, no bundle, service worker restarted — each must produce a documented verdict and an incident.
  • Definition of done for this feature: the coverage table in §5 is all green for the rows in scope, and every red row that remains is a written, agreed limitation in the customer documentation.

10. Glossary

TermPlain meaning
Extension / MV3A small program that runs inside Chrome or Edge. MV3 is the current rulebook Google requires extensions to follow.
Service workerThe extension’s background brain. It has no visible window, may be shut down when idle, and is out of reach of web pages.
Content scriptExtension code injected into a web page. It comes in two flavours: isolated (the page cannot touch it) and MAIN world (the page can).
Native messagingThe official pipe that lets a browser extension talk to a normal Windows program — here, our DLP agent.
fetch / XHRThe two ways JavaScript sends data to a server without reloading the page. Almost every modern upload uses one of them.
Multipart / resumable uploadSplitting a big file into many small pieces and sending them separately, so a dropped connection does not restart the whole upload. Used by S3, Google Drive and OneDrive.
Fingerprint / containmentOur detection maths. It compares a document against registered classified documents and reports how much of the registered content appears in it.
Fail-secure / fail-openWhat happens when the safety check itself breaks: fail-secure blocks (safe, sometimes annoying), fail-open allows (convenient, unsafe).
WFPWindows Filtering Platform — the Windows facility our agent uses to allow or block network connections per application and destination.
MinifilterOur kernel driver. It sits inside the Windows file system and can see, and refuse, any attempt to read a file.
mTLSMutual TLS: both sides prove who they are with certificates. Agents use it to talk to the management server.
