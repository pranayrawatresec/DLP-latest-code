00The premise correction — read this first

You asked to "first get the attestation certificate." There is no such object. Nothing named an attestation certificate is issued to you at any point in this process, and waiting for one will stall the release. Three different things get conflated under that name, and it is worth separating them before you spend a day looking for the wrong artefact:

What people call itWhat it actually isWhere you are
"The EV certificate" Your GlobalSign EV code-signing certificate on the SafeNet eToken. It does not let a kernel driver load. Its only two jobs here: prove your company's identity to Microsoft once, and sign the submission package each release. You have it
"The attestation certificate" Does not exist. The closest real step is the one-time Partner Center identity validation: Microsoft hands you a small binary file, you sign it with the EV cert, you upload it back. That unlocks the hardware dashboard. Nothing is issued to you — a flag flips on your account. Phase B below
The thing that actually matters The Microsoft-signed catalog (dlpflt.cat) that Partner Center returns after attestation signing, signed by Microsoft Windows Hardware Compatibility Publisher. This is what makes Windows load your driver without test mode. Phase I below
The one-sentence version

Since Windows 10 1607, the only signature a retail kernel loads is Microsoft's; your EV certificate is the key to the submission counter, not the signature on the driver.

Why your driver refuses to load today

It is signed with a self-signed test certificate, which is why every runbook in this repo tells the operator to run bcdedit /set testsigning on and reboot. Confirmed on this machine just now:

That error is the whole problem this document solves.

02The trust chain, end to end

Keep this picture in your head; every phase below is one arrow in it.

SafeNet eToken (EV private key, non-exportable) │ │ signs, once ▼ Partner Center identity validation ──► Hardware dashboard unlocked │ │ signs, every release ▼ dlpflt.cab ──upload──► Microsoft attestation service │ │ signs the catalog ▼ dlpflt.cat (Microsoft Windows Hardware Compatibility Publisher) │ ▼ Windows kernel Code Integrity accepts dlpflt.sys with test mode OFF
Note on the on-prem rule

CLAUDE.md says everything stays on the customer's premises. That still holds. This entire process happens at the vendor, on your build machine, before shipping. No customer data touches Microsoft — only your own driver binary. The customer's endpoint needs no internet to verify a Microsoft signature; the root is already in every Windows install. Air-gapped sites are unaffected.

03Phase A — Pre-flight on the signing PC

Do this before touching Partner Center. It takes five minutes and catches the failures that otherwise surface halfway through a submission.

A1 · Set up a shell with the tools on PATH

Run PowerShell as Administrator and paste this. Every later command assumes these variables exist, so keep this window open (variables do not survive a new shell).

PowerShell (admin) — session setup
$Kit      = "C:\Program Files (x86)\Windows Kits\10\bin\10.0.26100.0"
$SignTool = "$Kit\x64\signtool.exe"
$Inf2Cat  = "$Kit\x86\Inf2Cat.exe"
$StampInf = "$Kit\x64\stampinf.exe"

# Your EV certificate, by thumbprint — never by /a (which picks arbitrarily
# when several code-signing certs are in the store, and you have four).
$EVThumb  = "2CE7FCBEF04C279943F175A936E7588D298D254A"

# GlobalSign RFC3161 timestamp authority. DigiCert's works too and is a
# useful fallback:  http://timestamp.digicert.com
$TSA      = "http://rfc3161timestamp.globalsign.com/advanced"

$Repo     = "D:\DLP_GUIDE"
$Mf       = "$Repo\dlp-minifilter"
$Stage    = "$Repo\dlp-minifilter\build\submission"

Write-Host "signtool : $SignTool"
Write-Host "inf2cat  : $Inf2Cat"

A2 · Confirm the token is plugged in and the key is reachable

PowerShell — token check
$cert = Get-Item "Cert:\CurrentUser\My\$EVThumb"
$cert | Format-List Subject, Issuer, NotAfter, HasPrivateKey

# Expect:  Provider = eToken Base Cryptographic Provider
#          Private key is NOT exportable
certutil -user -store My $EVThumb | Select-String "Provider|Key Container|NotAfter"

Expected: HasPrivateKey : True and the eToken provider line. If HasPrivateKey is False or the cert is missing entirely, the token is unplugged or SafeNet Authentication Client is not running — open the SAC tray app and confirm the token shows as connected.

A3 · Prove you can actually sign with it

Sign a throwaway file. This is the moment you find out whether the PIN works, before you are mid-release.

PowerShell — signing smoke test
$tmp = "$env:TEMP\ev-smoke-test.ps1"
"Write-Host 'hello'" | Set-Content $tmp -Encoding utf8

& $SignTool sign /fd SHA256 /sha1 $EVThumb /tr $TSA /td SHA256 /v $tmp
& $SignTool verify /pa /v $tmp

A SafeNet dialog will pop up asking for the token password (the PIN). Type it there. Verification should report your GlobalSign chain and a timestamp.

Token lockout — the one irreversible mistake in this document

The SafeNet eToken locks permanently after a fixed number of wrong PIN entries (typically 15, and the counter does not reset on success in some configurations). A locked EV token means re-purchasing the certificate and repeating GlobalSign's organisation vetting — weeks, not days.

So: type the PIN by hand, do not loop a script that retries, and do not let CI guess. And per CLAUDE.md — secrets are never hard-coded or logged — never put the PIN on a command line. The single-logon / /csp+/kc unattended trick that circulates on Stack Overflow embeds the PIN in the process arguments, where it lands in command-line auditing, Sysmon, and shell history. Do not use it in this repo.

A4 · Confirm the INF is still submission-clean

Already passing as of today, but re-run it after any INF edit (especially the altitude change in Phase C):

PowerShell — signability test
$probe = "$env:TEMP\inf2cat-probe"
Remove-Item $probe -Recurse -Force -ErrorAction SilentlyContinue
New-Item -ItemType Directory -Force -Path $probe | Out-Null
Copy-Item "$Mf\dlpflt.inf"           $probe -Force
Copy-Item "$Mf\build\out\dlpflt.sys" $probe -Force

& $Inf2Cat /driver:$probe /os:10_X64 /verbose

Expected tail: Signability test complete. / Errors: None / Warnings: None.

04Phase B — Partner Center enrolment and EV validation

This is the step you were calling "getting the attestation certificate." It is a one-time account unlock, not a certificate issuance. Budget 1–3 business days — Microsoft's verification is not instant.

B1 · Prerequisites before you start the form

  • A Microsoft Entra ID (Azure AD) tenant for the company. If Resec has Microsoft 365, you already have one — enrol with that, not a personal account.
  • The legal company name in Partner Center must match the EV certificate subject exactly. Yours reads RESEC SYSTEMS PRIVATE LIMITED. A mismatch here is the single most common enrolment rejection.
  • Someone with authority to accept the Microsoft Hardware Program agreement.
  • The EV token physically present on the machine doing the signing.

B2 · Enrol in the Windows Hardware program

  1. Go to partner.microsoft.com/dashboard/hardware and sign in with the company Entra ID account.
  2. Choose to enrol in the Hardware (Windows Hardware Developer) program.
  3. Enter the legal business details. Use the identical spelling from the certificate subject.
  4. Accept the program agreement.

B3 · The EV validation file — the actual "attestation" step

The dashboard gives you a small binary file to download (historically named something like *.bin; the dashboard labels it as the code-signing verification file). You sign it with the EV certificate and upload it back. That signature is how Microsoft binds your certificate to your Partner Center account.

PowerShell (admin) — sign the Partner Center validation file
# Adjust the path to wherever you saved the download.
$Blob = "$env:USERPROFILE\Downloads\MicrosoftHardwareValidation.bin"

& $SignTool sign /fd SHA256 /sha1 $EVThumb /tr $TSA /td SHA256 /v $Blob

# Confirm before uploading — this must show RESEC SYSTEMS PRIVATE LIMITED.
& $SignTool verify /pa /v $Blob

Upload the signed file back into the dashboard. Wait for the account to show as verified.

Record this

When enrolment completes, Partner Center assigns your company a Seller ID and a publisher name. Write both into the release documentation — you will need them for every future submission and for any support conversation with Microsoft.

05Phase C — Request a Microsoft-assigned filter altitude

Start this the same day as Phase B, because it also takes days and it changes the INF you are about to sign.

A minifilter's altitude decides where it sits in the filter stack relative to antivirus, encryption, and replication filters. Yours is 265000, sitting in the FSFilter Content Screener band (260000–269998) — the right band for a DLP content screener, but self-assigned. Two filters that squat the same altitude on one machine is a support incident you cannot fix remotely.

C1 · Request it

  1. Email fsfcomm@microsoft.com — the Microsoft file system filter altitude allocation address.
  2. State: company name, filter name (dlpflt), the load-order group (FSFilter Content Screener), and a description of what the filter does (screens content written to removable media for data leak prevention).
  3. They reply with an assigned altitude in that band.

C2 · Apply it

Exactly one line changes in dlp-minifilter/dlpflt.inf:

dlp-minifilter/dlpflt.inf — [Strings] section
; before (development placeholder)
Altitude        = "265000"

; after (Microsoft-assigned — substitute your real value)
Altitude        = "26xxxx"

Then re-run the Phase A4 signability test, and grep the repo for the old value — the number is hard-coded in test scripts and runbooks that will otherwise silently check for the wrong filter:

PowerShell — find every hard-coded 265000
Select-String -Path "$Repo\*.md","$Repo\dlp-minifilter\*","$Repo\dlp-agent\*","$Repo\demo-vm\*" `
  -Pattern "265000" -Recurse -ErrorAction SilentlyContinue |

06Phase D — Build the release driver

Build from a clean tree so the binary you submit is the binary you can reproduce.

PowerShell (admin) — clean release build
Remove-Item "$Mf\build\out\*.obj","$Mf\build\out\*.sys","$Mf\build\out\*.cat" `
            -Force -ErrorAction SilentlyContinue

cmd /c "$Mf\build\build-driver.bat"

# Sanity: the binary exists and carries the right image characteristics.
Get-Item "$Mf\build\out\dlpflt.sys" | Select-Object Name, Length, LastWriteTime
Decide before you submit: /Od vs /O2

build-driver.bat compiles with /Od (optimisations disabled). That is a debug setting. Once Microsoft signs a binary, changing a compiler flag means a new submission — you cannot patch it. Either switch both cl.exe lines to /O2 now, or make an explicit, documented decision to ship unoptimised. A minifilter sits on every file I/O path on the endpoint; /Od on that path is a measurable cost.

The security-relevant flags are already correct and must stay: /GS /guard:cf /sdl /kernel on compile, /INTEGRITYCHECK /GUARD:CF /RELEASE on link.

07Phase E — Embed-sign the driver, stamp the INF, build the catalog

Order matters — get this wrong and the submission fails validation

Inf2Cat writes the hash of every file into the catalog. If you sign dlpflt.sys after running Inf2Cat, you change the file, the recorded hash no longer matches, and the package is broken. The order is always:

build → embed-sign the .sys → stampinf → Inf2Cat → makecab → sign the .cab

E1 · Stage a clean submission folder

Never build the CAB in the repo root — that is what left setup.inf/setup.rpt lying around in August.

PowerShell — stage
Remove-Item $Stage -Recurse -Force -ErrorAction SilentlyContinue
New-Item -ItemType Directory -Force -Path "$Stage\dlpflt" | Out-Null

Copy-Item "$Mf\build\out\dlpflt.sys" "$Stage\dlpflt\" -Force
Copy-Item "$Mf\dlpflt.inf"           "$Stage\dlpflt\" -Force

Get-ChildItem "$Stage\dlpflt"

E2 · Embed your EV signature in the .sys

Optional in the strict sense — Microsoft signs the catalog, not the binary — but do it anyway. The binary is linked with /INTEGRITYCHECK, and an embedded signature gives you a second, independently verifiable provenance claim on the file itself. It also survives if the catalog is ever separated from the driver.

PowerShell — embed-sign (token PIN prompt appears)
& $SignTool sign /fd SHA256 /sha1 $EVThumb /tr $TSA /td SHA256 /v `
    "$Stage\dlpflt\dlpflt.sys"

& $SignTool verify /pa /v "$Stage\dlpflt\dlpflt.sys"

Expected: chain RESEC SYSTEMS PRIVATE LIMITED → GlobalSign GCC R45 EV CodeSigning CA 2020 → GlobalSign Code Signing Root R45, plus a timestamp block. Not the "root not trusted" error from section 00 — that would mean you signed with the wrong certificate.

E3 · Stamp the DriverVer

Your INF currently has a hand-written DriverVer = 08/25/2026,1.0.0.0. Stamp it so the date reflects the actual build — Windows uses this to decide which driver package wins when two are present.

PowerShell — stampinf
& $StampInf -f "$Stage\dlpflt\dlpflt.inf" -d "*" -v "1.0.0.0" -a "amd64"

Select-String -Path "$Stage\dlpflt\dlpflt.inf" -Pattern "DriverVer"

-d "*" means "today". Bump -v for every release you submit; two submissions with the same version are a support headache later.

E4 · Generate the unsigned catalog

PowerShell — Inf2Cat
& $Inf2Cat /driver:"$Stage\dlpflt" /os:10_X64 /verbose

# Expect: "Signability test complete." with Errors: None / Warnings: None
Get-ChildItem "$Stage\dlpflt"

You now have three files in submission\dlpflt\: dlpflt.sys (EV-signed), dlpflt.inf (stamped), dlpflt.cat (unsigned). Do not sign the .cat yourself — Microsoft signs it, and your signature on it would simply be replaced.

/os:10_X64 is the right and only target here. Your INF has a single [DefaultInstall.NTamd64] section: x64 Windows 10/11 only. If you ever need ARM64, that is a separate INF section, a separate build, and a separate submission.

08Phase F — Build the CAB

Partner Center takes a CAB (for attestation) or an HLKX (for full WHQL). The CAB must contain the driver files inside a folder — not loose at the root — and it must include the catalog. That is exactly what the August attempt got wrong.

F1 · Write the DDF

PowerShell — write dlpflt.ddf into the staging folder
@'
.OPTION EXPLICIT
.Set CabinetFileCountThreshold=0
.Set FolderFileCountThreshold=0
.Set FolderSizeThreshold=0
.Set MaxCabinetSize=0
.Set MaxDiskFileCount=0
.Set MaxDiskSize=0
.Set CompressionType=MSZIP
.Set Cabinet=on
.Set Compress=on
.Set CabinetNameTemplate=dlpflt.cab
.Set DiskDirectoryTemplate=.

'@ | Set-Content -Path "$Stage\dlpflt.ddf" -Encoding ascii

Get-Content "$Stage\dlpflt.ddf"

DestinationDir=dlpflt is what places the files in a dlpflt\ folder inside the CAB. DiskDirectoryTemplate=. drops the finished CAB in the staging folder instead of creating a disk1\ subdirectory.

F2 · Run makecab

PowerShell — build the CAB from the staging folder
Push-Location $Stage
makecab /f dlpflt.ddf
Pop-Location

Get-Item "$Stage\dlpflt.cab" | Select-Object Name, Length

F3 · Verify the CAB contents before you sign it

Thirty seconds here saves a rejected submission. All three files must be listed, each under dlpflt\:

Expected — all three, folder-prefixed

09Phase G — EV-sign the CAB

This is the signature Microsoft checks to confirm the submission came from the company that owns the Partner Center account. Same certificate, same token, same PIN prompt.

PowerShell — sign the submission CAB
& $SignTool sign /fd SHA256 /sha1 $EVThumb /tr $TSA /td SHA256 /v `
    "$Stage\dlpflt.cab"

& $SignTool verify /pa /v "$Stage\dlpflt.cab"

What each flag is doing, since these matter

FlagWhy
/fd SHA256File digest algorithm. SHA-1 is rejected outright by Partner Center.
/sha1 $EVThumbSelects the certificate by thumbprint. You have four code-signing certs in this store, three of them test certs — /a would be a coin flip. This flag is about the SHA-1 identifier of the cert, not the signature algorithm.
/tr $TSARFC 3161 timestamp. Not optional. Without it, everything you signed stops validating the day the certificate expires — 18 Aug 2027. With it, the signature stays valid indefinitely.
/td SHA256Digest algorithm for the timestamp itself.
/vVerbose — you want to see which certificate was actually used.
Timestamping needs internet

The signing machine needs outbound access to the TSA at signing time. This does not affect the air-gapped customer site at all — verification of an existing timestamp is offline. If the build machine is itself isolated, sign on a connected release box instead of dropping /tr.

10Phase H — Submit to Partner Center

  1. Sign in at partner.microsoft.com/dashboard/hardware.
  2. Drivers → Submit new hardware.
  3. Give the submission a name you will recognise in six months — e.g. dlpflt 1.0.0.0 amd64 attestation.
  4. Upload $Stage\dlpflt.cab (the signed one).
  5. Partner Center detects it is a CAB rather than an HLKX and routes it to attestation signing automatically. There is no separate "choose attestation" toggle to hunt for.
  6. Fill in the Requested Signatures checkboxes. See the box below — this is the step that trips people up.
  7. Submit, and wait. Attestation signing is usually minutes to a few hours — no hardware lab, no HLK test run.

Scope limit you must confirm against your customer contracts

Attestation signing covers Windows 10 (1607+) and Windows 11 client SKUs only. It does not cover Windows Server, and it does not grant the "Certified for Windows" logo.

This repo sells to defence, government and critical-infrastructure customers. If any deployment puts the agent on Windows Server — jump boxes, terminal servers, RDS session hosts are all realistic in those environments — attestation is not enough and you need full WHQL / HLK certification, which is a materially larger project (hardware lab, HLK controller, test passes, weeks of lead time). Find out now, not after the first Server deployment fails to load the driver.

Download the signed package from the submission page. It is a ZIP with the same folder layout you uploaded, under drivers\dlpflt\.

What actually comes back — measured 2026-09-23

The embedded signature is good news for Phase J: it means kernel Code Integrity can validate dlpflt.sys on its own, without needing the catalog registered first — so the pnputil catalog-registration worry is much less likely to bite.

PowerShell — unpack and verify the Microsoft signature
$Signed = "$Mf\build\signed"
Remove-Item $Signed -Recurse -Force -ErrorAction SilentlyContinue
Expand-Archive "$env:USERPROFILE\Downloads\<downloaded>.zip" -DestinationPath $Signed

# Locate the returned files (folder depth varies by submission).
$cat = (Get-ChildItem $Signed -Recurse -Filter dlpflt.cat | Select-Object -First 1).FullName
$sys = (Get-ChildItem $Signed -Recurse -Filter dlpflt.sys | Select-Object -First 1).FullName
"cat: $cat"; "sys: $sys"

# THE test: does the catalog vouch for the driver, under kernel policy?
& $SignTool verify /v /kp /c $cat $sys
This is what success looks like

The output must name Microsoft Windows Hardware Compatibility Publisher in the signing chain. That string is the entire point of the exercise. If you see GlobalSign or Resec instead, you are looking at your own catalog, not the returned one.

/kp means "verify against kernel policy" rather than the default Authenticode policy — it is the check that actually predicts whether the driver will load.

Also verify the embedded signature on the binary itself

PowerShell — embedded signature, kernel policy
& $SignTool verify /v /kp $sys

Expect the same Microsoft Windows Hardware Compatibility Publisher chain. Do not expect the returned .sys to hash-match what you submitted — it will not, because the signature was inserted into it. The INF is the file that should come back byte-identical; check that one instead:

PowerShell — the INF must be unchanged
(Get-FileHash "$Stage\dlpflt\dlpflt.inf").Hash
(Get-FileHash (Get-ChildItem $Signed -Recurse -Filter dlpflt.inf | Select -First 1).FullName).Hash
# These two must be identical.

12Phase J — Prove it on a clean machine with test mode OFF

This is the acceptance test. Do it on the VMware VM, but first take a snapshot — your memory notes record that a wedged agent silently blocks all USB and the service will not stop cleanly.

J1 · Turn test signing OFF and reboot

Every prior runbook in this repo turned it on. Turn it off, or you are not testing anything.

On the test VM, elevated — then REBOOT
bcdedit /set testsigning off
bcdedit /enum "{current}" | findstr /i testsigning
# Reboot now. The setting does not take effect until you do.
shutdown /r /t 0

After the reboot, the "Test Mode" watermark in the bottom-right corner of the desktop must be gone. If it is still there, the setting did not apply and the test is invalid.

J2 · Remove the old test-signed driver and its test certificates

Otherwise you cannot tell whether the driver loaded because of Microsoft's signature or because a test root is still trusted in the VM's store.

On the test VM, elevated — clean slate
fltmc unload dlpflt 2>$null
sc.exe stop dlpflt   2>$null
sc.exe delete dlpflt 2>$null

# Remove the self-signed test roots that made the old driver loadable.
Get-ChildItem Cert:\LocalMachine\Root, Cert:\LocalMachine\TrustedPublisher |
  Where-Object { $_.Subject -match "DLP Mflt Test|DLP Minifilter Test|WDKTestCert" } |
  ForEach-Object { "Removing: $($_.Subject)"; Remove-Item $_.PSPath -Force }

J3 · Install the Microsoft-signed package

Copy the three returned files (.sys, .inf, .cat) into one folder on the VM, then:

On the test VM, elevated — install via the driver store
# Adds the package AND registers the catalog with Code Integrity.
pnputil /add-driver dlpflt.inf /install

# Then the DefaultInstall section, which creates the dlpflt service.
RUNDLL32.EXE SETUPAPI.DLL,InstallHinfSection DefaultInstall 132 .\dlpflt.inf

fltmc load dlpflt
fltmc filters
Expect to iterate on exactly this step — here is why

Attestation signing signs the catalog, not the binary. For the kernel to accept a catalog signature, that catalog has to be registered in the system catalog database (%SystemRoot%\System32\CatRoot). pnputil /add-driver does that registration; InstallHinfSection on its own historically does not, and your tools\install.ps1 uses InstallHinfSection alone.

So the sequence above deliberately runs pnputil first to register the catalog, then InstallHinfSection to create the service from the DefaultInstall section (pnputil /install will not create a service for a non-PnP INF like this one).

If fltmc load still fails with a signature error, the catalog is not being seen. Fallback: register it explicitly with signtool catdb -v dlpflt.cat, or confirm the file landed under C:\Windows\System32\CatRoot\{F750E6C3-38EE-11D1-85E5-00C04FC295EE}\. This is the single step in the whole document most likely to need a round of trial and error — plan for it rather than treating it as a failure of the signing.

13Phase K — Wire the signed driver into the release package

dlp-agent\packaging\build-package.ps1 already picks the driver up. Reading it: it copies dlp-minifilter\build\out\dlpflt.sys, dlp-minifilter\dlpflt.inf, and dlp-minifilter\build\out\dlpflt.cat if present — so the catalog is treated as optional today. For production it is mandatory.

Copy-Item $sys "$Mf\build\out\dlpflt.sys" -Force

Follow-up edits this unlocks

  • build-package.ps1 — make a missing dlpflt.cat a hard failure for release builds, not a silent skip. Shipping a package with no catalog produces a driver that will not load, with no build-time warning.
  • tools\install.ps1 — it warns loudly when test signing is off. For a production-signed driver that warning is now backwards and will confuse operators. Add the pnputil /add-driver step from J3.
  • tools\uninstall.ps1, packaging\install-endpoint.ps1 — same review for test-signing assumptions.
  • Operator docs — DEPLOY-AND-TEST-GUIDE.md, ON-PREM-DEPLOYMENT-GUIDE.md, USB-DEMO-RUNBOOK.md and the VM runbooks all instruct a bcdedit step that a defence customer's policy may outright forbid. Split them into "lab (test-signed)" and "production (Microsoft-signed)" paths.
  • .gitignore — it currently ignores /dlp-minifilter/build/out/*.cat. The Microsoft-signed catalog is a release artefact you may want retained. Decide deliberately, and add setup.inf, setup.rpt, *.cab and build/submission/ while you are there.
  • Delete the stale byproducts — D:\DLP_GUIDE\setup.inf and setup.rpt from the August attempt.

14Also sign the user-mode agent

While the token is plugged in. dlp-agent.exe is user-mode, so it needs no Microsoft involvement — your EV signature alone is enough, and it is what stops SmartScreen warnings and gives the customer's own application-control policy something to trust.

PowerShell — EV-sign the agent binary
& $SignTool sign /fd SHA256 /sha1 $EVThumb /tr $TSA /td SHA256 /v `
    "$Repo\dlp-agent\target\release\dlp-agent.exe"

& $SignTool verify /pa /v "$Repo\dlp-agent\target\release\dlp-agent.exe"

Sign the release binary before running build-package.ps1, since that script copies it into packaging\out\. Same applies to any future MSI — sign the MSI too.

16Hard rules

Never
  • Never re-sign dlpflt.sys after Microsoft returns it. The returned catalog records that exact binary's hash. Touching the file invalidates the attestation and you will not understand why it stopped loading.
  • Never put the token PIN on a command line or in a script. CLAUDE.md: secrets are never hard-coded or logged. Command lines are logged by more things than you think.
  • Never retry a wrong PIN in a loop. A locked EV token costs weeks and a re-purchase.
  • Never ship the test certificates. tools\dlpflt-test.pfx, build\out\dlpflt-test.cer, dlpflt-signer.cer stay in the lab. A customer machine trusting your test root is a genuine vulnerability — anyone with that PFX can sign a kernel driver that machine will load.
  • Never rely on bcdedit /set testsigning on in production. It weakens the boot trust chain and defence customers commonly forbid it by policy.
  • Never sign a build you have not functionally tested. Re-submission is cheap but not instant, and each one is a new version number.
Always
  • Timestamp every signature (/tr + /td SHA256).
  • Select the certificate by thumbprint (/sha1), never /a — four code-signing certs live in this store.
  • Keep the exact build that was submitted, plus the returned package, archived per release. If Microsoft ever revokes or you need to reproduce, you cannot rebuild bit-identically from source alone.
  • Build → embed-sign .sys → stampinf → Inf2Cat → makecab → sign .cab. In that order, every time.
  • Bump DriverVer for every submission.

17Open decisions — answer these before submitting

None of these block you from starting Phase A or B today, but each one, answered late, means re-signing.

  1. Windows Server? If any customer runs the agent on Server, attestation is insufficient and you need WHQL/HLK. This is the biggest scope risk in the document.
  2. Altitude before or after first submission? Requesting it first (Phase C) means one submission instead of two. Recommended: request now, submit once.
  3. /Od or /O2 for the release driver? Decide before Phase D.
  4. ARM64? Currently amd64-only. If a customer has ARM64 endpoints, that is a separate INF section, build and submission.
  5. HVCI / Memory Integrity compatibility. Untested so far and increasingly on by default in hardened environments.
  6. Certificate expiry: 18 Aug 2027. Renewal means a new token and re-validating the Partner Center account. Put it in the calendar now, with three months of lead time.
  7. Where does the token live? A single EV token that can sign kernel drivers for defence customers is one of the most sensitive objects the company owns. Decide custody, storage and the procedure if it is lost — before it is routine.
