How The Classifier Decides Sensitive

Every step traced to the function that performs it, for the at-rest sweep specifically — what actually happens between "the walker finds a file" and "the fusion layer calls it sensitive."

Achieved · verified on the test VM, including 5 hard power-offs · 22 September

The save gap is closed: the agent's files are never missing or half-written after a crash.

This was the first open item for the at-rest channel. The walker's bookmark (ml-walk.checkpoint.json) and its coverage record (ml-walk.completed.json) were saved by deleting the old file, then renaming the new one into place. A crash between those two steps left no file at all. The same pattern was in two other places, including the fingerprint index.

What changed

One shared safe-save routine, src/atomicfile.rs, now does every save the agent makes. It never deletes the old file first. It writes the new version to its own temporary file, flushes it to disk, then swaps it in with a single rename. If another program is holding the file, it retries for up to 1.5 seconds instead of giving up.

It is used by 12 save sites: the walker's bookmark and coverage record, the fingerprint index, the ML verdict log and its key, the eight policy and identity files in storage.rs, and the USB incident queue.

Found and fixed along the way

  • A new fingerprint index is used without a restart. Every channel loaded the index once at start-up, so a newly downloaded one was ignored until the service restarted. They now pick it up within 3 seconds and keep the last good copy in memory if the file disappears. Verified on the VM: 11 of 11 checks passed, and an endpoint that started with no index was enforcing again within 3 seconds.
  • The ML verdict cache no longer switches itself off. One failed tidy-up of its log (antivirus holding the file) used to stop every later save until a restart.
  • One damaged queued incident can no longer block every incident behind it. It is now set aside so the rest reach the console.
  • The driver no longer serves a stale "clean" answer. The kernel driver kept each file's read-deny verdict for as long as the file stayed in the system cache, and never checked whether it was decided under the current index. So a document read yesterday stayed readable after it was registered today. Fixed in dlpflt.c (both the normal-read and memory-mapped paths); verified on the VM, 6 of 6: the old driver asked the agent 0 times after a reconnect, the fixed one asks again.
  • A newly registered document is enforced without a restart, end to end. Registered in the console, index v5 compiled at 09:49:56, the VM downloaded it at its next check-in, both channels switched to it 1.3 s later, kguard reconnected 0.7 s after that, and an untrusted read of the document was denied 19 s after the download (idm=1). The service kept the same process ID throughout.

Power-cut test: passed. A writer using the new routine and a writer using the old delete-then-rename pattern ran side by side while the VM was hard powered off five times. The new routine's file was complete and valid every time. The old pattern's file was missing once and zero-filled four times: its name survived but its contents never reached the disk.

Honest limit: the writer uses the agent's exact save routine, so this is the direct proof. The agent's own files surviving is supporting evidence only, since the agent saves them every few minutes and none of the cuts necessarily landed on one of those saves.

The same thing, in beginner terms

  1. The bookmark

    The at-rest sweep reads through every document on the disk, like reading a very long book. Every so often the agent saves a bookmark file that says "I've got up to here", so after a restart it can carry on instead of starting over. When it finishes it saves a second file, a "finished" certificate, which some security features wait for.

  2. The old way

    To update the bookmark, the agent wrote the new one on a sticky note, threw the old bookmark away, then put the sticky note in the book. If the computer crashed or lost power in the moment between "throw away" and "put in", the book had no bookmark at all.

  3. Why it was done that way

    A comment in the code said Windows cannot swap one file for another in a single step, so the old one had to be deleted first. We tested that on both machines. It isn't true: Windows can swap them in one step.

  4. The new way

    Write the new bookmark on a sticky note. Make sure the ink is really dry, meaning the data is actually on the disk and not just in memory. Then swap it in with one movement. At every moment the book has a complete bookmark, either the old one or the new one. It never has none, and never a half-written one.

  5. If someone is holding it

    Sometimes another program, such as antivirus, is holding the bookmark while it checks it. Before, the agent gave up and waited until the next save, 200 files later. Now it waits a moment and tries again.

  6. What it means for you

    After a crash, a reboot or a killed service, the agent always finds a complete, readable file. The worst case is losing the last few seconds of progress, never the whole file. We tested this by pulling the plug on the test machine five times in the middle of saving: the new way came back complete every time, the old way came back missing or blank every time. Because every save now goes through the same routine, the fix covers the fingerprint index and the policy files too, not just the bookmark.

At-rest channel: substantially fixed. Full ML pipeline: not production-ready.

The mechanism is sound and now measured. Two blockers outside this channel still gate the ship.

The classification math (chunking, pooling, softmax, thresholding) is correct, tested against golden vectors, and now runs at a realistic sweep time after last round's fixes. That is a genuine, verified improvement to the at-rest channel specifically.

It does not make the product deployable on its own. The prior full-pipeline audit found the ONNX session mutex is shared between this sweep and the kernel's synchronous write scan (engine.rs:501,547) — a large document being classified can stall the 500 ms driver budget and latch an unrecoverable circuit breaker. That defect is in shared code the at-rest fixes did not touch. It is still there.

The pipeline, step by step

src/ml/*.rs

This is the at-rest path specifically: walk.rs discovers a file, everything past extraction is shared with the at-creation watcher and the on-demand queue — one classification function, three producers.

  1. Eligibility gate

    src/ml/filter.rs:231 should_classify — src/ml/walk.rs:1031

    The walker lists a directory and, for each file, checks extension, size, and directory exclusions before spending anything on it. As of last round, the walker's default extension set is DOCUMENT_EXTENSIONS (docx, xlsx, pptx, pdf, zip, txt, md, csv, tsv) — not the full extractor-supported list. A .py or .json file is skipped by the sweep, not by the classifier: the at-creation watcher and the on-demand read path still classify it the moment it is actually touched.

  2. Read the prefix, compute the cache key

    src/ml/walk.rs:1202 process → src/ml/cache.rs read_for_classification

    The walker reads at most the first 4 MiB of the file — contract C1: this must be the exact prefix the kernel driver hashes on the read path, or a verdict computed here could never be found later. The cache key is SHA-256 of that prefix. For a handful of container formats (docx/xlsx/pptx/zip/pdf) whose parsers need bytes past the 4 MiB mark, the read is escalated to the whole file for extraction — but the KEY stays pinned to the 4 MiB prefix either way.

  3. Cache check — cheap path

    src/ml/walk.rs:1217

    self.cache.get(&key, model_version). If this exact content, under this exact model version, was already classified — by any of the three producers — this is a HashMap lookup and nothing else runs. This is also where last round's fix applies: a hit refunds the rate-limiter token it cost to reach this point, so re-sweeping an already-covered estate is actually cheap.

  4. Miss → extract text

    src/ml/queue.rs classify_job → detect::extract_text

    On a miss the walker hands the bytes to the shared background queue, which calls the extractor: plain decode for text formats, a real parse for docx/xlsx/pptx/pdf/zip. No text extracted (an image, an encrypted archive) is not an error — it is the outcome Barren, and nothing is cached.

  5. Truncate, then chunk

    src/ml/engine.rs:349 prepare · src/ml/chunk.rs

    Text is truncated to max_chars = 200,000 characters (a compatibility constant, matches the sidecar the model was exported with) before tokenizing. What survives is split into overlapping windows sized to the model's own geometry:

    max_tokens = 512  ·  overlap_tokens = 64  ·  min_tokens = 32

    Content budget per chunk is 512 − 2 special tokens = 510; each chunk after the first advances 510 − 64 = 446 content tokens, so consecutive chunks share a 64-token seam rather than cutting a sentence in half at a hard boundary.

  6. Encode each chunk, mean-pool [CLS]

    src/ml/engine.rs run_split

    Chunks are pushed through the ONNX encoder in groups of micro_batch_size (default 8). Each group emits one 768-wide [CLS] vector per chunk; these are accumulated into a running f64 sum and the group's activations are dropped before the next group loads — this is what bounds memory to one micro-batch instead of the whole document. After every chunk has passed through:

    pooled = (Σ cls_i) / chunk_count   —   one 768-wide vector for the entire document

    The mean is exact regardless of batch size — summing then dividing once is mathematically identical whether it happens in one pass or eight — which is why the split graph and the old single-call monolithic graph produce byte-identical labels (verified to 2.1×10⁻⁶ max logit divergence in the golden-vector tests).

  7. Classification head, once

    src/ml/engine.rs run_split, head pass

    The single pooled vector runs through the head network exactly once, producing 29 raw logits — one per business-function label. This is the one step that is not decomposable across batches (the head is non-linear), which is the whole reason the split design pools first and classifies once rather than averaging per-batch answers.

  8. Softmax, then argmax

    src/ml/engine.rs:404, :626 softmax
    p_i = exp(logit_i − max(logits)) / Σ exp(logit_j − max(logits))

    The max-subtraction is not cosmetic: without it a large logit overflows exp() to infinity and every probability becomes NaN, which would then be compared against a policy threshold — tested directly (softmax_does_not_overflow_on_a_large_logit). The winning label is the highest-probability index; ties go to the lowest index, matching NumPy's argmax.

  9. Label lookup

    src/ml/labels.rs:38 LABELS (frozen array, index = model output position)

    The output index is looked up in a hand-kept, compile-time-length-checked array of 29 entries — FIN (Finance), NUC (Nuclear & Strategic Systems), GOV (Government Reporting), and so on. The model itself carries no label names; a re-ordering of this array would silently relabel every prediction the endpoint makes, which is why the array is documented as frozen and the loader cross-checks its length against the sidecar on startup.

  10. Cache the model's answer — not a sensitivity verdict

    src/ml/cache.rs:238 CachedVerdict::from_prediction

    What gets written to the verdict cache is {model_version, label_id, confidence, chunks, tokens, truncated}. The sensitive boolean is deliberately not one of those fields — it doesn't exist yet at this point. This is the single design decision that makes a live policy change retroactive: an admin marking a new label sensitive changes the answer for every already-cached file on its next lookup, with no re-classification.

  11. Policy evaluation — where "sensitive" is actually decided

    src/mlpolicy.rs:160 MlPolicy::label_is_sensitive
    sensitive = policy.enabled AND label_id ∈ admin-selected labels AND confidence ≥ (that label's own threshold, else policy.min_confidence [default 0.70])

    This function runs fresh on every lookup — at read time, at write time, on every cache hit — never once at classification time. An unselected label never counts as sensitive no matter how confident the model is (a document correctly identified as PUB — Public Information — is not a leak, however certain the model is that it's PUB). This is the only place a label becomes a security-relevant fact.

  12. Fusion — the model can only add, never subtract

    src/detect/decide.rs:693 ml_blocks_egress · :726 ml_blocks_read
    sensitive_overall = fingerprint_hit OR ml_sensitive

    The ML signal and IDM/EDM fingerprinting are independent and additive. Fingerprinting can only recognise a document somebody explicitly registered; the model has never seen this specific document before and says only what kind of document it resembles. Neither signal can cancel the other — there is no code path where a positive fingerprint match is overridden by an ML "not sensitive" result, or vice versa.

A concrete run, with real numbers

Measured, not modelled

From the VM verification in the previous round — a 3,633-byte PDF, single chunk, cold cache:

content_len=3633  extraction=Ok { format: "pdf" }
idm=0  edm=0
ml="ok"  ml_label="GOV"  ml_confidence=0.9215904727874636
signal="ml"  severity="medium"  block=true

Walking it through the steps above: the file passed the eligibility gate (pdf is in DOCUMENT_EXTENSIONS) → the ≤4 MiB prefix was read and hashed → no cache hit → extracted to plain text → one chunk (under 510 tokens, no windowing needed) → one encoder pass, one head pass → softmax gave GOV a 92.16% probability → the console policy had GOV selected with the default 0.70 floor, so 0.9216 ≥ 0.70 → sensitive=true → fingerprinting found nothing (idm=0 edm=0) but the OR-fusion blocked anyway. Total time for extraction plus inference plus cache write, measured end to end through a live USB copy: 156 ms.

Production readiness — at-rest channel

What last round's fixes actually closed
  • Eligibility narrowed to DOCUMENT_EXTENSIONS by default — the 17.5-hour sweep for 126 real documents is now a ~48-minute sweep, verified against a real 232,719-file profile.
  • Re-sweeping an already-covered estate no longer re-spends rate-limiter budget — cache hits refund their token (RateLimiter::refund).
  • Directory descent is throttled — a source-heavy subtree with zero eligible files can no longer run unbounded.
  • denyUnclassified startup arming is model-version-aware — a stale completion record from a superseded model can no longer arm a fail-secure deny it didn't earn.
  • A targeted overflow re-sweep can no longer indefinitely defer the full estate-wide sweep.
  • OneDrive/SharePoint placeholder files are skipped rather than force-downloaded to be classified.
  • 341 tests pass, including 14 new ones written directly against these six fixes — the mechanism above is not aspirational, it's what the passing golden-vector and pipeline tests actually exercise.

What is still open in this channel specifically

  • Resolved, see the top of this page. The completion/checkpoint write used "temp file, then remove destination, then rename", so a crash in that window could lose the coverage record. It now goes through the shared safe-save routine (src/atomicfile.rs), verified on the VM, including 5 hard power-offs.
  • The pending-directory list is capped in what gets persisted to the checkpoint, not in what the walker holds in memory while a sweep is running.
  • ml::walk::run() — the real service loop, with real sleeps and a real stop flag — has no dedicated test. The fixes are tested at the level below it (Walker::step/drive with an injected clock); the loop itself is exercised only by running the actual service.

Is the ML pipeline production ready?

Not yet — and not because of at-rest

No. The at-rest channel is meaningfully improved, but two structural defects confirmed in the full pipeline audit live in code every channel shares, and neither was in scope for this round's fixes:

1. engine.rs:501,547 — the ONNX session mutex is held for an entire document and is shared between the background classify worker and the kernel's synchronous write scan. A large document being classified in the background can stall the 500 ms driver reply budget on an unrelated USB copy happening at the same moment.

2. dlp-minifilter/src/comms.c:605 — eight consecutive stalls of that kind latch an IPC circuit breaker with no detector and no automatic recovery. Past that point the endpoint blocks all USB egress until the service is manually restarted.

Both are real, both are reachable under the shipped configuration, and neither is specific to the at-rest sweep — they'd exist even if the walker were perfect. They were flagged as the two items to fix first in the original full-pipeline report, ahead of everything else, specifically because the 500 ms kernel contract makes them non-negotiable rather than schedulable.

Once those two are closed, the at-rest channel's role in the pipeline is no longer a limiting factor for shipping: the mechanism above is correct, the sweep now runs at a realistic cost, and it is covered by tests that would fail if any of the six fixes regressed.
