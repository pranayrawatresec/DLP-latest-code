Deployment & Operations

DLP Setup & Deployment

How the endpoint DLP is deployed and operated. The guiding rule: the administrator only ever uses the console — never a command line. This guide covers the one-time setup, how an endpoint self-configures, and how to turn on read-deny safely.

The operating model in one line

The admin sets policy in the console → the server stores it → each endpoint's agent (running as LocalSystem) pulls it at check-in and applies it to the kernel driver itself — registry mode/fail knobs and the volume attach. No reg add, no fltmc, no editing files on endpoints.

01 Management server (one-time, on-premises)

Runs on the customer's premises; works fully air-gapped. Node + PostgreSQL.

  1. Start PostgreSQL & run migrations

    The database schema (including the read-deny policy and trusted-applications tables) is created by the migration runner.

    docker compose up -d        # PostgreSQL 17 (dev)
npm run migrate             # apply schema migrations
  2. Create the first administrator

    No open signup ever — the first sysadmin is created by a CLI command on the server box, then everyone else is managed in the console under Administrators.

  3. Start the server

    It hosts the admin console (browser) and the agents' mutual-TLS endpoint. npm start.

02 Enrolling an endpoint

Done once per PC, at install time. After this the machine is fully console-managed.

  1. Create an enrollment token in the console

    Enrollment tokens → Create — one token per rollout wave, sized to the number of PCs.

  2. Install the agent on the PC installer

    The MSI drops the agent, the CA certificate, and the signed driver; registers the driver and the DLPAgent LocalSystem service; and enrolls using the token (exchanges it for a client certificate). This is the only step that runs on the PC, and the installer does it — the operator does not open a shell.

  3. The agent self-configures automatic

    On first check-in the service pulls the fingerprint bundle, the trusted-applications list, and the read-deny policy, and applies them. From here everything is driven from the console.

03 Turning on read-deny (all in the console)

Read-deny ships off — protection is inert until an admin turns it on. Roll it out safely, monitor → measure → enforce.

Important: read-deny is off until you enable it

The seeded read-deny policy is mode = off. The agent applies whatever the console says — so on a fresh system, read-deny does nothing until an admin sets the mode. (This is why setting a driver registry knob by hand has no lasting effect: the agent re-applies the console policy at the next check-in.)

  1. Curate Trusted applications

    Add the apps allowed to read sensitive files: Windows (path C:\Windows), Office, your PDF reader/browser, antivirus, backup, the DLP agent. Anything not listed is treated as untrusted under the allowlist posture.

  2. Open Read-deny policy and set the scope

    Choose the posture (Allowlist recommended) and the scope — removable USB is always protected; toggle the fixed drive and pick watched folders (e.g. \Users = all user files, or the whole \).

  3. Set mode to Monitor

    The endpoints detect and report what they would block, but allow it — nothing breaks. Watch the incident feed for exfil-read-would-block entries.

  4. Review, fill gaps, then switch to Enforce

    Every would-block that is a legitimate app → add it to Trusted applications. When the would-block feed is quiet, flip the mode to Enforce. The agent applies the change; no reboot or shell.

04 What the agent does for you (no CLI)

The manual commands used during development map to these automatic agent actions in production.

  • Sets the driver mode / fail behaviour — the agent writes the driver's registry values from the console policy (replaces reg add … ExfilReadBlockEnabled).
  • Sends the watched folders to the driver over its config channel.
  • Attaches the driver to C: via the filter-manager API when fixed-drive scope is on (replaces fltmc attach dlpflt C:).
  • Runs as LocalSystem, so it can see SYSTEM-context processes (a remote tool's privileged helper) and set the driver — this is why the service, not a hand-run guard, is the production form.
  • Fails secure offline — if the server is briefly unreachable, the agent keeps enforcing the last policy it saw.

05 Developer / test signing dev only

For a test VM only — NOT production. Production drivers are signed through the Windows Hardware Dev Center (attestation/EV), not a self-signed cert.

  • Create + trust a test code-signing cert on the test machine (tools\make-testcert.ps1), then bcdedit /set testsigning on and reboot.
  • Build + sign the driver (build\build-driver.bat, tools\sign-driver.ps1); load it with fltmc load dlpflt.
  • These CLI steps exist so engineers can verify the kernel engine in isolation. On a customer PC the installer + agent do all of this — the admin never touches the command line.

06 Operational notes to remember

  • Policy default is off. A freshly enrolled PC does not enforce read-deny until an admin sets the mode in the console.
  • Curate the allowlist before enforcing. Too narrow a list denies legitimate apps their own reads — always run Monitor first.
  • One global policy today. The read-deny policy currently applies to every endpoint; per-machine / per-group targeting is a planned addition.
  • Live-apply timing. A mid-run mode change applies at the endpoint's next check-in / service cycle (making it instant is a small planned refinement).
  • Everything is audited. Every console policy change and every endpoint block (including repeat blocks) is written to the tamper-evident audit log.
