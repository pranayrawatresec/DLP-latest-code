Content Detection Engine — Fingerprinting, EDM & the Protected Content Repository

Architecture and build plan for the "know the actual data" layer of the DLP: document fingerprinting (IDM), exact data matching (EDM), the server-side Protected Content Repository that admins feed, and the compiled index that ships to every Windows agent so verdicts work offline, on the endpoint, inside the air gap.

Winnowing
shingles + rolling hash (SIGMOD '03, same family as MOSS / commercial DLP)
On-endpoint
matching runs in the Rust agent — works with zero connectivity
Hashes only
endpoints never hold protected plaintext — only salted / one-way fingerprints
No new infra
PostgreSQL job queue, no Kafka — per the small-dependency rule

● Proposed — not yet implemented

1. The one big adaptation: match on the endpoint, author on the server

Cloud DLPs (Purview et al.) can afford to do matching in their cloud. We cannot and should not: our enforcement point is a Windows agent that must keep working fully offline (fail secure), and customer data must never leave the premises. That single constraint shapes everything below:

  MANAGEMENT SERVER (authoring side)                 WINDOWS AGENT (verdict side)
  ──────────────────────────────────                 ───────────────────────────
  Admin registers protected content                  USB copy / (later: email, upload, print)
        │                                                  │
        ▼                                                  ▼
  Extract → Normalize → Fingerprint                  Extract → Normalize → Fingerprint
        │                                                  │
        ▼                                                  ▼
  Protected Content Repository            ┌──────►  Local index lookup (Bloom → hash table)
        │                                 │                │
        ▼                                 │                ▼
  Index Compiler → signed, versioned  ────┘          Similarity score per protected doc
  INDEX BUNDLE (hashes only)                               │
  delivered via existing mTLS check-in                     ▼
                                                     Policy verdict: allow / audit / block
                                                           │
                                                           ▼
                                                     Incident (matched hashes) → server
                                                     server resolves hash→page/paragraph
                                                     for the analyst view (forensics)

Both sides run the identical normalize→shingle→hash algorithm — the server in Node (authoring, low volume), the agent in Rust (hot path). A shared golden test-vector corpus keeps the two implementations bit-for-bit compatible; this is the highest-risk integration point of the whole feature and gets its own test suite (§9).

2. Where each detector sits (the ladder) and when we build it

Design rule: every detector is a plug-in behind one interface — detect(extracted_text, file_meta) → findings[] — and the policy engine consumes findings, never raw detector internals. That's what lets OCR / ML / semantic slot in later without touching channels or policy.

3. The fingerprinting algorithm (IDM) — exact specification

3.1 Normalization (must be byte-identical in Node and Rust)

1. Decode to UTF-8 text (from the format extractor, §6)
2. Unicode NFKC normalize
3. Lowercase (Unicode-aware)
4. Replace every run of non-alphanumeric chars with a single space
5. Collapse whitespace; trim
6. Tokenize on single spaces → word stream

3.2 Shingle → hash → winnow

k-gram      : k = 8 consecutive words per shingle (sliding, overlap 7)
hash        : 64-bit FNV-1a over the joined shingle ("w1 w2 … w8")
winnowing   : window w = 8 hashes; keep the minimum hash per window
              (rightmost on ties) — the standard winnowing algorithm
guarantee   : any shared run of ≥ t = k + w − 1 = 15 words is detected
density     : ~2/(w+1) ≈ 22% of hashes kept → ~5.5× index compression

These are starting parameters, stored in the index bundle header (never hard-coded on the agent) so they can be tuned per deployment without an agent release. Raising w shrinks the index; raising k reduces coincidental matches on boilerplate.

3.3 Scoring — containment, not Jaccard

We ask an asymmetric question: how much of the protected document appears in the outbound file? A 3-page excerpt from a 100-page war plan must score high even though the outbound file is tiny relative to the source.

similarity(doc D, outbound F) = |fingerprints(F) ∩ fingerprints(D)| / |fingerprints(D)|

report both:
  containment  — % of D present in F      (drives block decisions)
  coverage     — % of F that came from D  (context for the analyst)

3.4 What survives, what doesn't (sets customer expectations honestly)

Detected
  • Rename, PDF→DOCX conversion, font/margin/layout changes
  • Copy-paste into another document or email body
  • Partial copies (pages, sections, tables) down to ~15 shared words
  • Added logos, headers, blank lines, reordered sections
  • Print→scan and screenshots — once OCR lands (D3), not before
Not detected (by IDM — by design)
  • Full paraphrase / rewrite (→ semantic layer, D4)
  • Content inside encrypted or password-protected containers (→ policy: unreadable + removable destination = block, fail secure)
  • Photos of screens taken with a phone (out of scope for an endpoint agent)

4. Exact Data Match (EDM) — specification

Authoring (server, air-gapped):
  1. sysadmin/policy_author registers an EDM source: a CSV/TSV export of an
     authoritative table + a schema (field names, types, which are "primary")
  2. per-field normalization by declared type
       text   → same pipeline as §3.1
       id     → strip separators/spaces, uppercase
       number → canonical digits, no grouping
       date   → ISO-8601
  3. hash = SHA-256(deployment_salt ‖ field_id ‖ normalized_value), truncated to 64 bits
  4. store hashes grouped by row → EDM index (plaintext export is NOT retained)

Matching (agent):
  tokenize outbound text → candidate values (words + typed patterns like id-shaped
  tokens) → normalize per type → hash with the same salt → look up
  RULE: fire only when ≥ N fields (default 2, at least one "primary")
        from the SAME row co-occur within a window of 300 normalized chars
Threat honesty — the salt lives on endpoints too. The agent must hash candidate tokens, so the deployment salt is present on every PC (DPAPI-protected, inside the encrypted index). An attacker who extracts it can dictionary-test guessed values against the index — a real risk for low-entropy fields (dates, 6-digit IDs). Mitigations: per-deployment random salt, index encrypted at rest, primary-field requirement (high-entropy fields like service numbers), and shipping only the collections an agent group actually enforces (§7). Residual risk is documented, not hidden — this matches how Purview EDM frames its salted-hash model.

5. Server side — the Protected Content Repository

Admins never see "generate fingerprint". They see collections of protected content:

  Collections                          Registration sources (v1 → v2)
  ───────────                          ──────────────────────────────
  Army Operations                      v1: file upload (single/multi) via console
   ├─ Deployment Orders               v1: server-local folder path (one-shot scan)
   ├─ Mission Briefings               v2: watched network share (SMB/UNC crawler,
   └─ Logistics Plans                      re-scan on interval, auto-register new files)
  DRDO Research                        never: SharePoint/S3/GDrive connectors —
   └─ Missile Designs                        air-gapped customers don't have them;
  Personnel (EDM source)                     the fileshare crawler covers the real case

5.1 Registration flow (async — uploads return immediately)

  POST /api/protected/documents  (multipart)         [authn session + authz: protect:write]

     │  outside the DB — same design the Phase-4 evidence store will use)

     │                                       air-gapped appliance. Postgres queues
     │                                       comfortably handle this volume.

5.2 Schema (new migration set)

protected_collections   id, name, classification, description, created_by, created_at
protected_documents     id, collection_id, title, status, current_version, created_by, created_at
document_versions       id, document_id, version_no, blob_ref, sha256, size_bytes, mime,
                        page_count, registered_by, registered_at, retired_at NULL
document_fingerprints   version_id, hash BIGINT, seq INT      -- seq = position, server-side
                        PRIMARY KEY (version_id, seq), INDEX ON (hash)
edm_sources             id, name, schema_json, salt_id, row_count, status, created_by, created_at
edm_hashes              source_id, row_id INT, field_id SMALLINT, hash BIGINT, INDEX ON (hash)
processing_jobs         id, kind, ref_id, state, attempts, last_error, run_after, created_at
index_bundles           id, version, scope_json, params_json, sha256, signature, size_bytes,
                        built_at
  • Versioning: re-uploading a document creates a new document_versions row; old versions stay matchable until explicitly retired — a leak of last month's v1 is still a leak.
  • Positions (seq) stay server-side only. The agent reports which hashes matched; the server maps them back to page/paragraph for the analyst ("pages 17–19 of ArmyDeploymentOrder.pdf, 231 fingerprints"). Keeps the endpoint index small and the forensic story strong.
  • Originals kept, encrypted, access-gated: enables re-fingerprinting when algorithms improve and side-by-side comparison during investigations. sysadmin cannot read originals (separation of duties — same rule as evidence); every access is audited.

6. Text extraction — the bounded-format decision

Extraction is the largest dependency surface in this feature, and it exists twice (Node worker + Rust agent). We bound it hard:

7. The index bundle — compile, sign, distribute

  BUNDLE LAYOUT (binary, little-endian)
  ┌───────────────────────────────────────────────────────────────┐
  │ header    magic, format_ver, bundle_ver, params {k, w, hashbits},
  │           salt_id, scope (collection ids), built_at            │
  │ bloom     Bloom filter over all IDM+EDM hashes (~10 bits/entry,
  │           <1% FP) — the fast-reject path for 99.9% of files     │
  │ idm       sorted u64 hash → (doc_version_id, collection_id)    │
  │ edm       sorted u64 hash → (source_id, row_id, field_id)      │
  │ docs      doc_version_id → {title-hash, collection, fp_count}  │
  │ sig       Ed25519/RSA signature by the management CA — agent   │
  │           verifies before load; unsigned bundle = rejected     │
  └───────────────────────────────────────────────────────────────┘

  DISTRIBUTION — rides the existing mTLS check-in, no new channel:
  agent check-in payload  += { index_version: N }
  server response         += { index: { latest: M, download: /agent/index } }
  agent: if M > N → GET /agent/index (mTLS) → verify sig → swap atomically
         → store encrypted at rest (DPAPI/TPM-bound key)
  offline: agent keeps enforcing with the last good bundle — fail secure.

Size budget: a 200-page document yields roughly 10–15k winnowed fingerprints ≈ 120 KB. A 10,000-document estate lands around 1–2 GB fleet-wide — too big to ship wholesale. Two levers, both designed in from day one: scoping (bundles are compiled per agent-policy-group; an agent only receives collections its policies reference) and winnowing density (raise w for very large corpora). Delta updates (v2) reduce steady-state traffic; v1 ships full bundles per version bump, which is fine at pilot scale.

8. Agent side — the detection engine crate

dlp-agent/src/detect/
  mod.rs        pub fn verdict(path) -> Verdict        ← the ONE entry point channels call
  extract.rs    bounded-format text extraction (§6)
  normalize.rs  §3.1 — byte-identical to server
  shingle.rs    k-grams, FNV-1a, winnowing
  index.rs      bundle load, signature verify, Bloom + binary-search lookup, atomic swap
  edm.rs        token candidates, typed normalize, salted lookup, proximity rule
  score.rs      containment/coverage per doc, EDM row grouping

Verdict {
  file_hash_match:  Option<doc>,                    // exact SHA-256 (D1)
  idm:  Vec<{ doc_version, collection, containment, coverage, matched_hashes }>,
  edm:  Vec<{ source, rows_hit, fields }>,
  regex: Vec<{ rule, count }>,
  extraction: Ok | Unreadable(reason),               // Unreadable → policy decides
}
  • Performance budget: Bloom-negative (the overwhelmingly common case) < 1 ms for a 10 MB file; full match on a positive < 50 ms. Matching is pure CPU + one mmap'd index — no I/O waits.
  • Callers: USB v0/v1 call it post-copy for audit incidents (value ships before any driver exists); the v2 minifilter calls it pre-completion for true blocking; future channels (email, upload, print) call the same function.
  • Incidents carry the matched hash list + scores → server resolves to pages/paragraphs via document_fingerprints.seq → analyst sees "97% of ArmyDeploymentOrder.pdf v2, pages 17–19" — deterministic, evidence-grade attribution.

9. Policy integration

rule "army-ops-usb" {
  channel:      usb                       # later: email, upload, print
  collections:  ["Army Operations"]
  idm:          { block_at: 0.90, warn_at: 0.70, audit_at: 0.40 }   # containment
  edm:          { source: "Personnel", min_fields: 2, action: block }
  unreadable:   block                     # encrypted container to USB ⇒ deny
  file_hash:    block
}

Thresholds are per-rule, not global — an NDA template and a war plan deserve different sensitivity. Every triggered rule writes an incident and an audit entry; every block is explainable from stored evidence (which doc, which version, how much, where).

12. Open decisions

  • Shingle unit: word-level k=8 (proposed, robust to layout) vs character-level k≈50 (better for CJK/no-whitespace text). Parameterized either way; pick after corpus testing.
  • Fuzzy hashing (ssdeep/TLSH) as a cheap secondary detector: nice for binaries/CAD where text extraction fails — proposed skip in v1 (another dependency, overlaps with IDM on text).
  • Bundle scoping granularity: per agent-policy-group (proposed) vs per-agent. Group-level is simpler and matches how policies will be assigned.
  • Where the salt is provisioned: generated at EDM-source creation, delivered inside the encrypted bundle (proposed) vs per-agent-group salts (stronger, multiplies index builds).
