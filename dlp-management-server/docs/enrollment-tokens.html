Enrollment Tokens

The one bridge between the human admin plane and the machine plane. A sysadmin mints a one-time secret; an agent spends it once to enroll and receive its certificate. This is how a logged-in human's authority becomes an agent's authority — no separate agent-authorization system.

A brand-new PC has no identity yet, so it can't use a certificate to prove it belongs. The enrollment token is the bootstrap proof that the customer's IT sanctioned this install — the only thing that lets a machine cross from "unknown" to "trusted".

3. Security best practices applied

  • 256-bit CSPRNG token, prefixed dlpenr_ for leak-scanners
  • Only SHA-256(token) stored — raw value never persisted or logged
  • Raw token returned exactly once, with a one-time warning
  • Atomic conditional UPDATE → no double-spend under concurrency
  • Two-gate pattern: requireAuth then requirePermission
  • Soft revoke — audit history never deleted
  • Generic failure to the agent; real reason only in the audit log
  • Input caps: maxUses ≤ 10000, expiry ≤ 1 year, description ≤ 500
  • Every create / revoke / denial written to the hash-chained audit log
Why SHA-256 here, but bcrypt for passwords? A password is low-entropy and human-chosen, so it must be slow-hashed (bcrypt) to resist brute force. An enrollment token is 256 bits of CSPRNG output — there is nothing to brute-force, and we need an O(1) exact-match lookup by hash. A fast hash is the correct choice; bcrypt would be both wrong (salted, un-lookup-able) and pointless here.

4. The atomic redemption — the crux

The one security-critical operation. A single conditional UPDATE makes "check the token is still usable" and "consume one use" one indivisible step. Postgres row-locks the matched row, so if 25 agents present the same single-use token at once, exactly one can move use_count from 0→1 while the guard still holds; the rest match zero rows.

UPDATE enrollment_tokens
   SET use_count = use_count + 1
 WHERE token_hash = $1
   AND revoked = false
   AND (expires_at IS NULL OR expires_at > now())
   AND use_count < max_uses
 RETURNING id, use_count, max_uses;      -- 1 row = success, 0 rows = refused

Verified live: 25 concurrent redeems of a single-use token → exactly 1 winner, 24 rejected, use_count never overshoots 1. No SELECT … FOR UPDATE round-trip, no held transaction.

6. A real bug this testing caught (and fixed)

E20 failed on the first run — the audit chain broke. Root cause: the audit canonicalizer treated a Date in a log entry's detail as an empty object {}, while the value actually stored in the jsonb column was the Date's ISO string. So the hash written and the hash recomputed on verification disagreed the moment any entry carried a Date (the token's expiresAt was the first). Fix: normalize detail through the same JSON round-trip that jsonb storage performs, and handle Date explicitly in the canonicalizer — so the hash is always computed over exactly what verification later reads back. This is precisely the kind of latent tamper-evidence bug that only end-to-end testing surfaces.
