1. The core principle: monitor mechanisms, not channels

“Dropbox”, “Google Drive”, and “WeTransfer” are not three engineering problems — they are one HTTPS-upload hook. The whole channel-coverage effort collapses from ~40 targets to ~10 enforcement points, each covering a family. The agent is content-and-channel based, not identity-based: it asks only “are sensitive bytes crossing a monitored boundary in a form I can read?”. It does not care whether the process is Word or malware.exe — which is exactly why the same hook that stops a careless employee also stops unsophisticated exfil malware.

    built: IDM/EDM/ML)     ⑥  Print subsystem                     ──▶  paper · print-to-PDF · fax

One detection engine, many channels. Every file-bearing mechanism calls the same verdict() you already built and tested (IDM fingerprinting + EDM + future ML). The channel work is plumbing that feeds bytes into that engine and acts on its answer — not new detection logic each time.

4. The mechanisms, in build detail

① Filesystem minifilter (kernel driver) — the workhorse
Intercepts IRP_MJ_CREATE/WRITE on any mounted volume pre-completion, asks the user-mode service for a verdict(), and allows / denies / shadow-copies. One driver covers USB, optical, SMB shares, mapped drives, disk staging, and cloud-sync folders (the file is a plaintext write to the sync folder before it is uploaded). This is the single highest-value component and the first thing to build. Cost: EV code-signing + Microsoft attestation, a real testing burden, and (for air-gapped sites) an offline driver-update story. Rust minifilter support is young — the pragmatic route is a small C/C++ driver with all logic in the Rust service over a FilterCommunicationPort.
② Device control (user-mode, no driver)
Reacts to device arrival (CM_Register_Notification), identifies it (VID/PID, serial, class, container ID), and applies allow / read-only / block via CM_Disable_DevNode, the Removable Storage Access policies, or Device Installation Restrictions. Essential for MTP/WPD (phones), which the minifilter cannot see because they never mount a filesystem. Also does USB-class allowlisting (“only issued encrypted drives”) and blocks USB network tethering.
③ Network filter (WFP)  +  ④ Browser/app/email hooks
WFP sees every outbound connection but only ciphertext for TLS — good for destination-blocking and volume-anomaly detection, blind to content. Real network content DLP must sit above the encryption: a browser extension / native-messaging host (web uploads, webmail body + attachment), an Outlook add-in / MAPI hook (desktop mail), or an enterprise TLS-inspection proxy with the corporate CA on the endpoint. This tier is where effort explodes — every app is its own integration — so prioritise by what the customer actually uses (usually webmail + one browser + Teams). Note the overlap with ①: many apps cache the outbound attachment to disk first, so the minifilter catches it even without an app hook.
⑤ Clipboard  ·  ⑥ Print — clean Tier-1 wins
Clipboard: WM_CLIPBOARDUPDATE to inspect copied text/data against verdict() before it can be pasted elsewhere (incl. into RDP sessions and cloud-clipboard sync). Print: a print provider / port monitor spools the job through content inspection, covering paper, network printers, and print-to-PDF/XPS (whose output file the minifilter also catches). Both are self-contained, don't fight TLS, and cover very common real-world leak paths.
⑦ Screen · ⑧ Remote/sub-OS · ⑨ Radios — deter or disable
Screen capture is only partially hookable (SetWindowDisplayAffinity per window, DXGI/BitBlt interception) and never stops a phone camera — pair a best-effort block with user-ID screen watermarking so any leaked image is traceable. Remote/session redirections (RDP/Citrix drive & clipboard, local VMs, WSL2's own network stack) are best handled by disabling the redirection/feature on a hardened build rather than intercepting it. Radios (Bluetooth, Nearby Share, WWAN, Phone Link): on a defence build the realistic answer is policy-disable the radio, not clever interception.

5. What we consciously place out of scope (Tier 4)

Naming these plainly is a credibility asset in a defence evaluation, not a weakness — it tells the customer which other controls must sit alongside the DLP.
  • The analog hole — photographing the screen, or scanning an on-screen QR code. No software stops it; mitigate with watermarking + physical/camera policy in secure areas.
  • Steganography — a document hidden inside an innocuous image defeats all content matching.
  • Covert protocol tunnels (DNS/ICMP) — WFP can throttle or anomaly-flag, not content-inspect.
  • TEMPEST / acoustic / optical emanation — physical-security and shielding territory.
  • A kernel-privileged adversary — can unhook the filter or read raw disk beneath it. DLP is defence-in-depth with EDR / least-privilege / OS hardening, never a standalone anti-APT guarantee.

6. Recommended build order — breadth per unit effort

  PHASE A  (Tier 1, clean, covers the most channels per mechanism)
    A1  Filesystem minifilter  ①            → USB · CD · SMB · sync folders · disk staging
        └─ first consumer of the verdict() engine you already built + tested
    A2  Device control          ②            → phones (MTP) · USB class allow/deny/read-only · tethering
    A3  Clipboard monitor       ⑤            → copy-paste · cloud clipboard
    A4  Print provider          ⑥            → paper · network · print-to-PDF

  PHASE B  (Tier 2, high value, harder — the content-on-network layer)
    B1  Browser hook            ④            → web upload · webmail (body + attachment) · cloud web UI
    B2  Outlook / mail hook     ④            → desktop email
    B3  WFP destination control ③            → dest blocklists, volume anomaly, covert-tunnel flags
    B4  Fail-secure on unreadable egress     → encrypted-container + monitored channel = block

  PHASE C  (Tier 3, policy-disable / deter — not custom interception)
    C1  Radio & feature policy  ⑨            → Bluetooth · Nearby Share · WWAN · Phone Link off
    C2  Session-redirection policy ⑧          → RDP/Citrix drive+clipboard, WSL2, VM sharing off
    C3  Screen watermark + capture block ⑦    → traceability over prevention

  OUT OF SCOPE (Tier 4) — documented, delegated to EDR / physical security / network egress control
Why this order. Phase A mechanisms are clean OS hooks that each cover a whole family of channels and reuse the existing detection engine — maximum coverage per unit effort, and the minifilter foundation is shared by every future file-based channel. Phase B is where the real adversary and the TLS problem live; it's essential but expensive, so it's scoped to the customer's actual app set. Phase C is configuration, not engineering. The strategic rule throughout: breadth beats depth — closing nine doors imperfectly beats bolting one shut while eight stand open.

7. How this connects to what's already built

  • The detection engine (IDM fingerprinting, EDM, future ML/semantic) is done and verified — every file-bearing mechanism above calls its single verdict() entry point.
  • The signed index bundle + mTLS distribution already ships policy/fingerprints to agents offline — every channel enforces from the same cached bundle, fail-secure when the server is unreachable.
  • Incidents already round-trip (agent verdict → server resolution → reviewer view); each new channel just tags its incidents with its own channel value (usb, print, web-upload…).
  • Next build = Phase A1: stand up mechanism ① (the minifilter) and wire the existing verdict() into the write path. The USB channel is not a new detection problem — it is the first consumer of the foundation already in place.
