Production-Readiness Audit

Read-Deny & Trusted-Reader Allowlist

Every finding that stands between the working RustDesk/AnyDesk block and a shippable feature — across the kernel driver, the Windows agent, and the management console. Each is explained in plain terms: what it is, and what actually goes wrong — including what still can't be done from the console.

scope: dlpflt.sys · dlp-agent · management-server + console method: code read + 2 parallel auditors

The one pattern to remember

Both auditors landed on the same theme independently: the allowlist is supposed to block anything not explicitly trusted, but in several places it quietly does the opposite — it lets things through and gives no warning that protection just switched off. That "fail-open" behaviour is the through-line of the red items below, and it's the exact opposite of the project's fail-secure rule.

Release-blockers

must fix before shipping

These either break normal use, silently turn protection off, or let a sensitive file leak. Nothing ships until these are closed.

1

Protection silently fails "open" in several situations

Blocker✓ Fixed
Agentexfil.rs:195, 290-300, 162-168, 242-272

In plain terms — The system is meant to block every program that isn't on the trusted list. But in four situations it does the reverse and lets everything through, with nothing telling the operator the machine is now unprotected: (a) if the guard can't identify a program, it treats it as trusted instead of untrusted; (b) if listing the running programs briefly fails, it sends the driver an empty set, which wipes out all blocking; (c) if the trusted list is empty, it blocks nothing; (d) if the guard isn't running with full privileges, it can't even see system-level programs (this was the original RustDesk-helper gap) — and it never checks or logs whether it actually has those privileges.

FixFail secure: unidentifiable → treat as untrusted; on an enumeration failure keep the previous set instead of clearing it; warn loudly on an empty list; verify + log elevation and privilege state at startup.

2

A file opened during startup can be marked "safe" forever

Blocker✓ Fixed
KernelAgentkguard/mod.rs:927-933, 816-820 · dlpflt.c:1755

In plain terms — When the agent first starts, there's a brief window before it has loaded its "what counts as sensitive" fingerprints. During that window it can't recognise anything, so it answers the driver with "this file is fine." The driver remembers that answer permanently. So a classified document that happens to be read in those first few seconds gets stamped safe — and stays safe even after the agent knows better. Confirmed on both sides: the agent sends a success+allow reply, and the driver caches it as a clean verdict.

FixWhen the agent can't actually classify, reply with a distinct "couldn't scan — don't cache" status; invalidate cached verdicts when the fingerprint bundle loads.

3

One over-broad rule turns the whole feature off

Blocker✓ Fixed
ServerAgenttrustedReaders.js:31-46 · trustedreaders.rs:104-123

In plain terms — An admin can add a trusted rule like C:\ or C:\Users — a folder so broad it covers everything. That single rule marks every program on the computer as trusted, which switches read-deny entirely off. The server accepts it with no breadth check, the agent happily matches every program against it, and nothing warns the admin they just disabled the control they were configuring.

FixServer rejects drive-roots and too-shallow paths and validates each rule type properly; the agent defensively ignores drive-root path rules.

4

Open-time blocking breaks creating new / empty files

Blocker✓ Verified on VM
Kerneldlpflt.c:1720-1734 (DlpExfilClassifyAndCache)

In plain terms — The new open-time block reads a file to decide if it's sensitive before letting a program open it. But an empty or brand-new file has nothing to read yet — so the fail-safe assumes the worst and blocks the open. The result: once the C: drive is watched, ordinary untrusted programs can't create or open their own new files, so normal apps start failing. (The old read-time path didn't have this problem because it skipped empty reads.)

FixAt open, block only on a positive sensitive match (known-bad hash or a real fingerprint hit); let genuinely unreadable/empty content pass and be judged on the real read.

Important

fix before a real rollout

Not instant showstoppers, but each is a real gap that will bite in a live deployment — missing safety rails, blind spots in the audit trail, or operational dead-ends.

5

No "watch without blocking" (monitor) mode

Important✓ Verified on VM
KernelAgentUIconfig.rs:316-323 · TrustedReaders.jsx:197

In plain terms — Blocking is only fully on or fully off. There's no mode that watches and reports what it would block without actually blocking. So you can't safely find out which legitimate apps you forgot to add to the trusted list — you discover them by breaking people's machines the moment you turn it on. Worse, the admin screen already tells operators to "roll out in monitor mode first" — a mode that doesn't exist.

FixAdd a monitor posture (log + raise incidents, but allow) end-to-end; fix the UI copy until it exists.

6

Watched-folder check matches text anywhere in the path

Important✓ Verified on VM
Kernelcomms.c:424 (DlpUnicodeContainsCI)

In plain terms — The driver decides whether a file is in a watched folder by checking if the folder text appears anywhere in the file's path, not whether the path actually starts with it. So watching \Users also accidentally covers unrelated folders that merely contain the letters "Users." Scope becomes broader and fuzzier than intended — and could be gamed. (The agent's own path logic is correct here; the driver's isn't.)

FixMatch on a real path prefix at a folder boundary, not a substring.

7

Repeat blocks aren't written to the audit log

Important✓ Verified on VM
KernelAgentdlpflt.c DlpAuditSilentDeny · kguard/mod.rs deny_drain_loop

In plain terms — The first time a file is blocked, it's logged. Every block after that is handled instantly inside the driver and never reaches the logging code. So if a program hammers a sensitive file fifty times, the security log shows one attempt, not fifty — the audit trail under-counts exactly the events an investigator cares about. For a product whose selling point is a complete tamper-proof audit, that's a real gap.

Fix & verifyThe driver now records one deny event per open (a per-open handle context, so distinct processes each count — the earlier per-file flag could not) at every cache-served deny path; the guard drains the ring and raises a repeat-deny incident that posts to the console feed. VM-verified: a second untrusted reader of an already-flagged file is blocked, drained (count=1), and posts its own incident — with no double-count of the first attempt.

8

A reboot silently leaves the C: drive unprotected

Important✓ Verified on VM
KernelAgentDlpReadScanScope (comms.c) · write_scan_scope (readdenypolicy.rs)

In plain terms — Watching the C: drive was set up at run time, after the guard connects. But on a reboot the driver attaches to drives before the guard is up — saw no watch config — so it skipped C: and never retried. Every restart quietly left the C: drive unwatched until someone manually re-ran the attach command. (Removable USB drives are unaffected — they're always watched.)

Fix & verifyThe agent now writes the fixed-drive scope (ExfilScanFixed + ExfilWatchPaths) into the driver's service registry key on every policy apply, and the driver reads them at DriverEntry (before any volume mounts) — so InstanceSetup attaches C: from the first instant of boot, no agent needed. VM-proven: with the seed written and the DLPAgent service stopped, reloading the driver attaches C: on its own (fltmc shows C: attached while the agent is stopped). The live DLP_CONFIG message still applies mid-run updates.

9

Rules typed on an endpoint can't be removed centrally

Important✓ Verified on VM
AgentServerConsolereadersAuthority · with_synced_readers · compute_untrusted_pids

In plain terms — Trusted rules written directly in a machine's local config were merged with the central list, and the console could only ever add trust, never subtract it. So if a bad or over-broad rule (like #3) sat in a local file, an admin couldn't revoke it from headquarters — they'd have to physically touch every affected machine.

Fix & verifyA console Trusted-apps authority switch on the read-deny policy: Merge (default, unchanged — union of local + central) or Central — the console list is the WHOLE allowlist, so local rules are ignored and HQ can revoke any trust. For the defence posture, Central + an empty console list = fail-secure lockdown (every non-agent process untrusted; the agent itself stays trusted); Merge keeps the "empty = unconfigured, enforce nothing" behaviour. VM-verified both ways: under Central a cmd read of a sensitive file — cmd being locally trusted via C:\Windows — is BLOCKED; back on Merge the same read is allowed while an untrusted reader stays blocked. Also observed fail-secure with the server offline (kept the last central policy).

10

The agent's own encryption helper gets blocked

Important✓ Fixed
Agentexfil.rs:181 · kguard/mod.rs:26-37

In plain terms — The agent has a separate helper process that legitimately reads files in order to encrypt them. Only the main agent process is exempted from blocking, so this helper is treated as untrusted and denied the reads it needs — quietly breaking the encrypt-on-write feature unless someone remembers to add the agent to its own trusted list.

FixAutomatically trust the agent's own installed binaries, independent of the admin-authored list.

11

A change can be saved without its audit record

Important✓ Fixed
ServertrustedReaders.js:84-103, 115-124

In plain terms — When an admin adds or removes a trusted rule, the change is saved to the database first and the tamper-proof log entry is written second, as a separate step. If the server crashes in between, the change is done but there's no record of who made it — a hole in the "every change is logged" guarantee. Deleting a rule is the worst case: the rule vanishes with no trail.

FixWrite the change and its audit entry in a single database transaction so they succeed or fail together.

12

Publisher cache grows forever and can be tricked

Important✓ Fixed
Agentexfil.rs:339-357

In plain terms — The agent remembers each program's publisher and never forgets, so memory grows without limit — and an attacker can inflate it on purpose by launching many oddly-named programs. It also remembers by file location, so if a trusted program's file is swapped for a malicious one at the same path, the agent keeps trusting the old, good identity.

FixCap the cache (evict oldest) and key it on the file's identity (size/timestamp/hash) so a swapped file is re-checked.

13

Checking every file at open time adds overhead

Important⏳ Deferred — do later (do NOT weaken open-deny)
Kerneldlpflt.c (DlpPostCreate open-deny)

In plain terms — The old design inspected a file only when it was actually read. The new open-time block inspects every file an untrusted program opens — which is far more often. On a broadly-watched folder, an untrusted app that touches many files pays a cost on each one's first touch, which can noticeably slow it (and the machine) down. Cost is bounded: only untrusted processes, only in-scope files, only the first touch of each file (then it's cached and every later open is O(1)).

Why the "obvious" fix is WRONG — The naive fix (act on cache hits at open, judge a never-seen file on the read) reopens the exact hole open-deny exists to close. RustDesk/AnyDesk does not read the file as itself: it opens the file, then hands the byte-read to a Windows/Explorer helper, so the read shows up as "Windows did it," not RustDesk. Read-time blocking decides on the requestor PID — which is the helper, not RustDesk — so it misses the leak. That is precisely why the decision was moved to OPEN time (deny RustDesk's open before it can delegate). Deferring the first encounter to the read would let any never-before-seen sensitive file leak on first touch. So open-deny stays; do not defer to read-time.

Plan (later)Keep open-deny as-is — the cost is largely inherent: to deny the open of a possibly-sensitive file you must inspect content to know it's sensitive, and you can't safely pre-skip by size or extension (that would leak large or renamed sensitive files). Reduce the cost WITHOUT weakening the guarantee: (1) narrow the watch scope in policy (specific folders like \Users\finance, not the whole \ C: drive) — the main amplifier; (2) skip 0-byte files at open (no content to match — the one provably-safe skip); (3) move the classify to a pended open — the open is not completed until the verdict (so nothing leaks), but the calling thread isn't held spinning, which helps a busy machine (same total work, better responsiveness). Do NOT adopt the read-time-first or fire-and-forget async options — both concede the RustDesk delegate window.

14

A stolen or revoked signing certificate is still trusted

Important⏳ Deferred — do later
Agentexfil.rs:650 file_signature_is_trusted — fdwRevocationChecks = WTD_REVOKE_NONE

In plain terms — Under the allowlist posture a publisher rule trusts any program signed by a given vendor (e.g. "Adobe Inc."). WinVerifyTrust checks the signature is valid and its certificate chains to a trusted root — but the flag WTD_REVOKE_NONE tells it to skip the revocation check. A certificate can be valid-looking and revoked at the same time; the agent never looks. So if a trusted vendor's code-signing cert is stolen (supply-chain) or revoked after a breach, the agent still trusts anything signed with it — malware signed with a stolen "Microsoft"/"Adobe" cert would be classed a trusted reader and allowed to read sensitive files. That is exactly the supply-chain / insider scenario this product exists to stop, and the one signal that would catch it is off.

Why it's off (the tension) — Revocation (CRL/OCSP) normally needs to reach the CA's servers over the internet. The product's non-negotiable rule is that everything works with no internet (air-gapped sites). Left on at an air-gapped site, the check would hang on network timeouts or fail — so it was disabled. Closing the gap therefore requires an offline revocation source.

Plan (later)Option A — offline CRLs via the update pipeline: the vendor pre-downloads the trusted publishers' CA CRLs and ships them to endpoints through the same offline channel as fingerprint bundles; the agent verifies revocation using only locally-cached data (WTD_CACHE_ONLY_URL_RETRIEVAL + whole-chain) so it never touches the network. Standard semantics, but the CRLs must be kept fresh. Option B — console-managed "blocked certificates" list (recommended, best fit for air-gapped defence): the admin maintains revoked/blocked signer thumbprints in the console, synced to agents like the trusted-reader list; the agent rejects any signer whose thumbprint is on it. Fully offline, central-authority — HQ adds a compromised cert once and every endpoint stops trusting it. Option C — minimum: surface/document in the console that revocation isn't checked, so operators know the residual risk. Leaning: B + C. Decide the option when we pick this up.

15

Duplicate-rule prevention ignores capitalisation

Important✓ Fixed
ServertrustedReaders.js (case-insensitive dedup) · migration 011 (CI unique index)

In plain terms — The "no duplicates" guard on the list is case-sensitive, but Windows matching ignores case. So winword.exe and WINWORD.EXE are stored as two separate rules that mean the identical thing — the list fills with confusing near-duplicates and the duplicate-blocker doesn't actually work.

FixThe route normalises (unify separators, trim trailing slash) and rejects case-insensitive duplicates before insert (lower(value) = lower(...) under the audit chain lock → clean 409). Hardened at the DB too: migration 011 adds a functional UNIQUE index on (match_type, lower(value)), so winword.exe/WINWORD.EXE can never coexist even if the app path is bypassed — DB-verified (a direct case-variant insert is rejected with 23505).

Low / polish

11 items
Name-only rules are easy to fake

A "trust by program name" rule trusts anything with that name — rename malware to winword.exe and it's trusted. Warn when a name rule has no path/publisher constraint.

~2-second gap for brand-new programs

A freshly launched untrusted program has up to ~2s before it lands in the block set. Inherent to the polling design — document the window rather than claim "instant."

Only the first 4096 programs are checked ✓ Fixed

On a very busy machine, programs beyond a fixed 4096 buffer are never listed, so never blocked. Grow-and-retry the buffer.

Accented publisher names may not match

Publisher comparison only case-folds plain English letters, so an accented vendor name typed in a different case can miss. Use full Unicode case-folding.

Noisy logging of every process ID ✓ Fixed

The agent logs the full list of hundreds of process IDs every ~2s at normal log level — noisy and exposes system layout. Drop to debug / rate-limit.

Reported content size is trusted blindly

The agent trusts the byte-count the driver reports without confirming the bytes arrived. Low risk (the kernel is trusted) but worth validating.

Bad delete-id returns a server error ✓ Fixed

An out-of-range id in a delete request produces a 500 instead of a clean "not found." Cap the numeric range.

Length limits live only in app code

The value/note length caps are enforced in the route, not the database, so any other write path is unbounded. Add database length checks.

List endpoints have no size limit

Both the admin and agent list endpoints return the entire table with no paging. Fine while small; note it before the list can grow large.

Recycled file IDs could carry a stale verdict

Rare: Windows can reuse an internal file id, and a cached sensitive/clean verdict could briefly apply to the wrong file. Mitigated by the epoch reset.

Confirm cancelling an open is always safe

Verify the open-cancel call behaves for every open type (create/overwrite, oplocks, transactions) — pairs with blocker #4's scoping.
