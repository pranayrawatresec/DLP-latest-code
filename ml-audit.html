On-Premise Endpoint DLPML Classification PipelineV6.2.01 · DistilBERT · split ONNX

ML Pipeline Readiness Audit

All three ingestion channels — at rest, at creation, on write — examined for defects, resource cost and deployability, with every claim adversarially re-tested before it was allowed to stand.

Verdict · Not deployable today

One structural defect gates the ship. Everything else can be scheduled.

The ML classifier is serialised behind a single mutex that is held for an entire document (engine.rs:501,547), and the single-threaded kguard message loop must take that same mutex to answer the kernel. A background sweep, a cache compaction, or one inline 200,000-character write scan therefore parks the driver's 500 ms FltSendMessage wait. Eight consecutive parks latch DLP_BREAKER_THRESHOLD — and once latched, the agent has no detector and no recovery short of a service restart, while the endpoint sits in total-block fail-secure.

The second gate is deployment, not code: [ml] enabled defaults true, the endpoint installer stages no model, and stage-ml-model.ps1 cannot stage the split pair at all. The documented rollout therefore produces an endpoint that either blocks all egress or loads the ~5 GB monolithic graph onto an 8 GiB PC.

Fix first: a bounded, non-blocking session acquisition on the enforcement path — try_lock with an immediate unavailable fallback, a hard per-document deadline, and max_chunks defaulted to a real number instead of 0 = unlimited. That single change converts all four inference-path blockers from "the endpoint can be driven into a latched, unrecoverable outage" into "the write scan occasionally reports unavailable, which fail_block already handles correctly." It is the only item on this list that the 500 ms kernel contract makes non-negotiable.

The rescan interval cannot keep up. DEFAULT_RESCAN_INTERVAL_SECS is 6 h, which admits 43,200 candidates at 120/min. A measured profile has 125,744 — 2.9× over. Above roughly 43,200 eligible files the walker never returns to idle, which is the opposite of the "backstop measured in hours" the module claims.

The root cause is the eligibility set, not the rate

filter.rs:60-68 admits 45 source and config extensions alongside the 5 real document formats. On the measured box, 62,750 .html + 30,865 .py — Python and library documentation — were 74.5% of the entire sweep. The pipeline spends 17.5 hours to classify 126 files. Splitting the extension list into a document tier (swept by default) and a source tier (opt-in) takes that sweep from 17.5 hours to about 48 minutes, at zero cost to safety: the on-demand read path still classifies a .py the instant it is read on an exfil channel.

A second, cheaper win: DEFAULT_EXCLUDED_COMPONENTS is missing site-packages, venv (only .venv is listed), vendor, packages, .tox, .next, and AppData\Local\Packages. Pruning happens before read_dir, so these are strictly free.

A re-sweep costs the same as the first sweep. The rate-limiter token is taken at walk.rs:955, before the code knows at walk.rs:1094 that the file is already cached. So an already-classified file costs a full token — directly contradicting the module's own claim that a repeated sweep "is cheap by construction."

The weights are not memory-mapped

The module documentation at engine.rs:70-71 states "the 256 MB model is memory-mapped by ONNX Runtime." This is false for the code as written. The entire session builder is three lines (engine.rs:852-855) and sets no mmap option, no arena configuration, no disable_cpu_mem_arena. commit_from_file therefore parses the protobuf and materialises every initializer into the private heap, plus additional pre-packed copies of the MatMul weights at optimisation Level 3. That is why the floor is ~350 MB rather than the ~30 MB a genuinely mapped 253 MiB graph would cost.

Loaded eagerly, never unloaded, replicated per session

The session loads at service start (main.rs:712-716) and unloads only when the policy goes inert. Worse, the load happens before the role is consulted (main.rs:712 vs :768), so every per-logon clipboard-agent and browser-host carries its own ~268 MB copy — even though those roles are documented as lookup-only and never run inference.

Minimum RAM to publish: 8 GiB is workable for a single-user desktop but leaves little headroom during a sweep. Publish 8 GiB minimum, 16 GiB recommended, and treat RDS/multi-session hosts as unsupported until the per-process duplication is fixed.

Blockers

6 confirmed · 3 distinct defects
Blocker

The write up-call runs DistilBERT inference inline inside the driver's 500 ms wait

dlp-agent/src/kguard/mod.rs:1216 · dlp-minifilter/src/dlpflt.c:1047 · comms.c:666

The code asserts that "the driver is not blocked on our reply the way the read up-call is, so the model runs inline on the async budget." That is false. dlpflt.c calls the same DlpQueryVerdict for DLP_REASON_WRITE as for read, and comms.c:666 arms one timeout for both.

A user copies a 300 KB .docx to USB with a cold cache. The agent extracts ~120k characters, chunks to ~70, and runs ~9 single-threaded encoder passes — several seconds against a 500 ms budget.

FixTreat write like read: cache lookup only, enqueue the miss, accept that a first copy is fingerprint-only — or keep the inline classify but behind a hard deadline with an unavailable fallback.
Blocker

A latched circuit breaker is unrecoverable without a service restart, and nothing detects it

dlp-minifilter/src/comms.c:605

Once ConsecutiveTimeouts reaches 8, DlpQueryVerdict returns STATUS_PORT_DISCONNECTED before ever calling FltSendMessage. Because the send is short-circuited, no live reply can arrive, so the only reset is reconnection at comms.c:176. Nothing in the agent detects the state.

Following the previous finding: one multi-second inline classification stalls the loop while ordinary read up-calls keep arriving. Eight time out. The breaker latches. From that moment the user cannot copy anything to any USB device until the service is restarted.

FixA liveness watchdog: track time since the last FilterGetMessage returned; past ~4 × timeout × threshold, close the port handle and reconnect, which resets the breaker.
Blocker

The inference mutex is shared between the background worker and the kguard message loop

src/ml/engine.rs:501, 547 · counted twice in the raw list

run_split takes sessions.lock() once and holds it for the whole document — every encoder micro-batch plus the head. The background classify worker and the kguard loop are threads of the same process sharing one engine, therefore one mutex. The kguard loop is strictly serial.

The sweep enqueues a large report; the worker holds the mutex for ~5 s; the user drags a file to USB; the message-loop thread blocks. Every read up-call in that window burns its 500 ms budget. This is the mechanism behind both blockers above.

FixRelease and re-acquire per micro-batch inside run_split — the f64 accumulator is already batch-local, so correctness is unaffected — and give the enforcement path a try_lock with an unavailable fallback.
Blocker

Zip decompression is bounded per member but not in aggregate

shared-core · extraction path

A 4 MiB zip/docx/xlsx/pptx can inflate without an aggregate output ceiling. This runs as LocalSystem against files arriving from email, USB and the web — an OOM here is a crashed DLP agent, which is a security event, not just a reliability one.

FixBound total decompressed output across all members, not per member, and abort the extraction when the ceiling is hit.
Blocker

A PDF Form XObject that draws itself recurses without a depth limit

pdf-extract · reachable from the enforcement path

A self-referencing Form XObject produces unbounded recursion and a stack overflow. A stack overflow in Rust is an immediate abort — not a catchable panic — so catch_unwind in the thread supervisor does not save the process.

FixA recursion depth cap in the XObject walk, and extraction on a thread with a bounded stack so the blast radius is one document rather than the service.

What the critic found that the audit missed

Completeness pass

Files nobody opened

src/ml/labels.rs — the only place index→meaning lives — was named in the brief and never read by any finder. A one-row shift reports a NUC document as ADM and the policy then says "not sensitive." The compile-time guard checks only length, and the tests pin 5 of 29 indices. src/detect/edm.rs (444 lines) also went unread, yet it runs inside the same 500 ms budget every latency claim in this audit is built on.

The rescan schedule runs on the wall clock while the rate limiter runs on the monotonic clock

The token bucket is correctly jump-proof; the 6-hour schedule is not (walk.rs:520-525, 1287, 1308). On an air-gapped endpoint with no NTP, a backward clock correction disables at-rest classification for the length of the correction — with no log line — while a stale completion record keeps denyUnclassified armed.

The verdict log has no cross-process lock, and two writers are a documented mode

put appends at a handle position frozen at open. Running dlp-agent usb-guard beside the service — which the code's own comments describe as the way to debug an endpoint — puts two independent writers on one unsynchronised log, overwriting each other's records in place.

At-creation is the thinnest channel, and it has no test file at all

run_scope goes straight to ReadDirectoryChangesW with no initial enumeration and no catch-up pass. Every file created during a service restart, a reboot, or the 5-second supervisor restart window produces zero at-creation events, ever. The only backstop is the at-rest sweep — the component this audit proved cannot complete.

What is working correctly

190 behaviours positively verified

This half matters as much as the defects. The audit confirmed, with line-level evidence, that:

  • No lock is ever held across I/O or across a classify call in the walker. step() computes under the mutex and drops it before acting (walk.rs:855-858). Lock ordering is acyclic, and mutex poisoning cannot wedge anything — every acquisition recovers the inner value.
  • Checkpoint persistence is crash-safe. Temp-file write then rename; a corrupt, truncated, empty or wrong-version cursor is discarded with a warning and counted, never fatal, never half-interpreted.
  • A resumed sweep cannot claim coverage it did not achieve. A cursor is rejected on both a scope-list change and a model-version change. Pending-directory truncation is honest — beyond the cap it stores no list and restarts the scope rather than silently dropping directories.
  • A targeted re-sweep never renews the estate-wide coverage claim (walk.rs:1207-1215, asserted in tests).
  • Symlinks and reparse points are never followed, so a junction pointing at a parent cannot loop forever or turn a scoped sweep into a whole-volume one.
  • The agent's own state directory is excluded from both producers, which is what prevents the verdict-log write→notify→classify→write livelock.
  • Contract C1 holds everywhere: the cache key is always SHA-256 of the first ≤4 MiB even when the extended whole-file read is used, so a walker-written verdict is reachable from the driver's key.
  • A console policy change is honoured immediately against already-cached verdicts. The cache stores the raw prediction, not the sensitive boolean — no re-sweep needed, no stale-policy answers.
  • The classify queue never blocks and is bounded in both dimensions, with the byte budget maintained as an O(1) running total on push and pop.
  • The walker cannot block SCM's stop timeout, and stop latency inside a sweep is bounded to one step.
  • A panic in the walker or watcher does not kill the sweep forever — supervised_thread catches the unwind, logs, and restarts.
  • Trailing-dot and trailing-space path evasion is closed, matching Win32 resolution exactly, with tests.
  • Hidden and system files are deliberately not excluded — the right default for a DLP product.
  • The triple-classify race is closed: enqueue_keyed dedupes on the pending and barren sets, and pending is cleared only after classification returns.
  • A never-swept machine cannot arm denyUnclassified — the check is conjunctive on sweep completion, a live policy, and a running worker.
  • The split graphs are provably equivalent to the monolithic model and demonstrably live on your VM, with worst-case logit divergence of 2.1×10⁻⁶.

Fix order

Recommendation
  1. Bound the enforcement path's session acquisition

    try_lock with an unavailable fallback, a hard per-document deadline, per-micro-batch lock release in run_split, and max_chunks defaulted to a real number. Clears four of the six blockers. Non-negotiable — the 500 ms kernel contract makes it so.

  2. Add the breaker watchdog

    Detect a stalled message loop and reconnect the port. Without this, any future stall is still a permanent, silent, total-block outage.

  3. Cap decompression and recursion

    Aggregate output ceiling for zip families; depth limit for PDF Form XObjects; bounded stack for extraction. These are remote-input crashes in a LocalSystem service.

  4. Fix the deployment story

    Teach stage-ml-model.ps1 the split layout, verify SHA-256 before use, check the VC++ redistributable version at install, and make the service report STOPPED and exit on activation failure.

  5. Shrink the eligibility set, then stop paying for cache hits

    Document tier by default, source tier opt-in; add the missing directory exclusions; refund or skip the rate-limiter token on an already-classified file. Turns 17.5 hours into roughly 48 minutes and makes the 6-hour rescan interval meaningful again.

  6. Then re-measure the sweep on this VM

    Only after 1–5 will the seven-day sweep=1 have a single explanation rather than four candidate ones. The walker currently emits no periodic progress line and no queue-depth metric — add those first, or the next diagnosis will be guesswork too.

Caveats

What this audit does not establish

The scan-time arithmetic assumes ~80 ms per chunk, derived by dividing a documented "~640 ms at eight chunks" by eight rather than measured directly. The eligible-file ratio is measured on one developer machine; the light-profile and file-server ratios are estimates. Mean chunks per file is inferred from file sizes, not from extracted text length — HTML in particular extracts to far less than its byte size.

The root cause of your VM's stalled sweep is not established. Four mechanisms in this report could each produce it, and the walker emits too little telemetry to distinguish them from outside. I report the stall as measured fact and the mechanisms as candidates.

Separately: your test VM shut itself down cleanly roughly every 45–60 minutes today — not a crash, not host memory pressure, most likely a Windows evaluation-licence timer. That interrupted the final verification pass and will interrupt a video recording too.
